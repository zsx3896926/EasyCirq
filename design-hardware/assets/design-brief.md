# 需求摘要（G0 输入）

由 Agent 从对话、参考工程和资料中提取并填写，不要求用户逐格填空，也不向用户推送整张空表。只记录已经知道且影响设计与验收的字段；未知写 `待确认`，不编造默认值。确认后的值要转录到项目 `design-state.json` 的 `requirements.<key>`，G0 门禁读取那里；字段名与门禁定义见 [门禁定义](../references/design-gates.md)。

填写约定：

- `待确认`：缺少用户输入或证据，按未满足处理，会阻塞 G0。
- `not_applicable`：本项确实不适用，必须同时写原因（例：无显示）。
- `assumed`：Agent 的暂定假设，必须写 `assumption`/`source`，不能伪装成用户确认。
- 数值带单位和来源；范围写上下限，不只写典型值。
- 局部修改只记录目标、受影响约束和需要重新确认的字段，不重填全表。

## 1. 任务与交付边界

| 字段 | 本次记录 |
|---|---|
| 目标（一句话） | 待确认 |
| 进入阶段（S0–S5 / 已有工程改板） | 待确认 |
| 交付级别 `delivery_level`（原理图 / PCB / DRC 0 / Gerber / 实物） | 待确认 |
| 已有工程、版本、参考与必须保留项 | 待确认 |
| 交付物接收者与用途（自用验证 / 工程复核 / 打样 / 小批） | 待确认 |
| 验收方式（看什么、测什么、谁确认） | 待确认 |

交付级别按实际验收能力选择：画完 PCB 不等于可制造，DRC 0 不等于实物可用；多选时写清每一级的验收证据。

## 2. G0 需求字段

这些键与 `design-state.json` 的 `requirements` 一一对应。本项不适用时不要省略，写 `not_applicable` + 原因；门禁会逐项判定。

| 键 | 要回答的问题 | 本次记录 |
|---|---|---|
| `delivery_level` | 交付到哪一级：原理图 / PCB / DRC 0 / Gerber / 实物；每级对应的验收证据 | 待确认 |
| `size_limit` | 板框上限（宽×高，mm）、是否含安装耳/连接器外伸；来源是用户、外壳还是结构图 | 待确认 |
| `enclosure_mounting` | 有无外壳；安装孔数量/类型（PTH/NPTH）、孔径、中心到板边距离、螺钉/铜柱规格；无外壳写 `not_applicable` + 原因 | 待确认 |
| `assembly` | 手焊 / 嘉立创 SMT / 混合；直插件与细间距器件由谁装 | 待确认 |
| `quantity_budget` | 打样/装配数量、预算（CNY）；是否含运费、贴片费、钢网费要写清 | 待确认 |
| `usb_role` | 只供电 / 要数据；对应连接器与 CC/ESD 需求；无 USB 写 `not_applicable` + 原因 | 待确认 |
| `test_points` | 需要哪些测试点（如 +5V、GND、NODE、VREF、GATE）、形式（1.0 mm 焊盘 / 2.54 mm 排针）与装配后可达性 | 待确认 |
| `display` | 有无显示；类型、尺寸、接口、安装方式；无显示写 `not_applicable` + 原因 | 待确认 |
| `firmware` | 有无 MCU/固件；型号、烧录/调试接口、是否随硬件交付；纯硬件写 `not_applicable` + 原因 | 待确认 |
| `threshold_interaction` | 阈值如何设定/标定：电位器 / 按键 / 显示菜单 / 上位机；无阈值功能写 `not_applicable` + 原因 | 待确认 |
| `alarm_behavior` | 报警输出与动作：自锁 / 可静音 / 自动解除；LED 与蜂鸣器节奏、回差 | 待确认 |
| `environment_accuracy` | 工作温度/湿度/灰尘、测量精度、响应时间、断电恢复；按实际使用环境写，不默认“室内常温”即满足 | 待确认 |

## 4. 板级、机械与制造约束

- 层数/板厂/工艺：层数决策（2 层 vs 4 层）在方案阶段记录成本与可布性对比；未知写 `待确认`。
- 接口朝向、板边位置、最高器件、外壳内净空、锁定件/卡扣：
- 机械细节（板框、安装孔、插头空间、声孔、LED、NTC、应力释放）：转 [机械约束模板](docs/mechanical.md)，本摘要只留结论。
- 丝印/装配标识（极性、1 脚、板名/版本、DNP、测试点标签）：转 [丝印与装配模板](docs/silk-assembly.md)。
- 环境/可靠性/适用标准：未知不默认为满足；需要认证/安规签核时写清范围与责任人。

## 5. 假设、风险与未测项

- 假设（A#）：内容、依据、影响；写入 `design-state.json` 的 `assumptions`。
- 风险（R#）：内容、触发条件、影响、缓解措施；写入 `risks`，标明 `open/closed`。
- 未测项（U#）：尚未验证的功能、环境或装配项，写清需要什么证据；交付时不得省略。
- 阻断性未决项（O#）：写入 `open_items` 并标 `blocking: true`，未关闭前 G0 不通过。

## 9. 落盘格式（示例）

```json
{
  "requirements": {
    "delivery_level": {"status": "confirmed", "value": "原理图+PCB+DRC0"},
    "size_limit": {"status": "pending", "reason": "尚未取得用户/外壳给出的上限；outline-fit 的结果不是需求"},
    "display": {"status": "not_applicable", "reason": "无显示"},
    "firmware": {"status": "not_applicable", "reason": "纯模拟，无 MCU"}
  }
}
```

示例只展示 `confirmed`、`not_applicable` 与 `pending` 三种写法；实际 `requirements` 必须覆盖 §2 的全部键，不适用项写 `not_applicable` + 原因，不能省略。不要把 `outline-fit`、自动布局或已有板框的结果写成“用户上限”。

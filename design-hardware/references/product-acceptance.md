# 以原始用途验收，而不是以文件数量验收

## 定义少量真实场景
从用户最初目标提取核心使用场景、适用正常条件和必要异常恢复。每项记录输入/操作、期望响应/阈值、实际响应、证据来源、板版/程序/配置和状态。
不要把“用起来方便”直接当自动通过项；把它转成具体动作，例如首次配置、读到数据、识别设备、收到通知、断电重启恢复。只测实际需要的场景，不强推复杂云平台或冗长认证清单。

## 不同完成层次分别报告
| 层次 | 能证明什么 | 不能据此证明 |
|---|---|---|
| 图纸/规则回读 | 适用范围内工程连接/几何/规则与保存 | 程序可运行、实物功能已实现 |
| 构建/离线测试 | 指定版本程序已构建或相应测试通过 | 真实板已烧录、传感/执行正确 |
| 生产/装配检查 | 实际服务报告范围内的制造/焊接检查 | 整机业务功能已验收 |
| 烧录/启动 | 指定设备已写入或看到对应启动证据 | 网络/手机端/全部功能正常 |
| 端到端功能实测 | 所测版本和条件下原始场景实际发生 | 所有环境、长期可靠性、认证或量产通过 |

实测可来源于Agent现场工具/仪器或明确的用户反馈，注明来源和覆盖；不要冒充另一种证据。没有证据标待测，有反例标失败，前提不完整标有条件，不适用说明原因。

## 示例：土壤干燥手机提醒
按实际需求裁剪：
1. 接电后设备能启动并识别传感器；采集与校准记录对应实际土壤/条件。
2. 达到约定干燥条件时，正确手机/页面收到可识别设备的通知；记录延迟和实际服务路径。
3. 保持干燥不会按错误频率重复骚扰；恢复湿润后的状态符合约定。
4. 断网/断电等适用异常发生后，设备表现和恢复符合约定。
阈值、时延、续航等如未明确可先提建议，但不编造已测数值。仅有截图、发送日志、平台模拟数据或PCB DRC不足以关闭以上功能项。

## 失败与继续
定位属于供电/装配、引脚/驱动、校准/算法、通信/配置、用户交互还是机械环境；沿依赖链修复再复验。改动会影响其他已通过场景时复测相关项，不默认全部结果永远有效。
缺少样机/账号/仪器时记录准确卡点及可继续任务，保留可复现程序、工程、接线/测点和测试步骤；用户接手时只给当前必要一步，不把整个开发流程重新甩给用户。

## 最终交付
围绕原始目标说“目前哪些效果已实际验证、哪些尚未验证、还差什么”。附真实可编辑工程、程序/构建产物、适用的采购/制造/结构文件、配置与使用说明、测试与版本记录。
用户仅委托局部任务时以局部范围交付，并注明与完整产品的关系。完整idea未落地时可以交付阶段成果，但不能自行宣布“项目完成”；只在原始目标和约定范围获得实际验证后宣称相应功能可用。

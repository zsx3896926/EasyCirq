# 报警器电路的功能性错误（离线检查抓不到的那一类）

> **结论：我在 `P2` 上画的那块板，功能上不工作。**
> 离线门禁给的是 `✅ 可以下单`，11 项必查全过——但它不会响。
> 这不是门禁的 bug，是门禁**没有覆盖**这类问题的证据。

## 错在哪

我画的是：

```
U1:1 (OUT1) ── ALARM ── BZ1:1
BZ1:2 ── GND
```

LM393 的输出是**开集（open-collector）**：它只有一条到地的 NPN 通路。

| 输出状态 | OUT1 电位 | 蜂鸣器两端 | 结果 |
|---|---|---|---|
| 导通（比较器判定"响"） | 拉到 ~0.1V | 0.1V 与 GND 之间 | **无电压 → 不响** |
| 截止 | 高阻（悬空） | 悬空与 GND 之间 | **无电流路径 → 也不响** |

**两种状态都不响。** 这个接法在任何情况下都不工作。

## 正确接法

开集输出驱动负载，负载必须接在**电源与输出之间**，由输出拉低来导通：

```
VCC ── BZ1 ── OUT1        （输出拉低时蜂鸣器得电）
```

或者（更稳，推荐）用三极管：

```
VCC ── BZ1 ── NPN 集电极
NPN 发射极 ── GND
OUT1 ── NPN 基极（串 1k）
```

理由：5025 有源蜂鸣器典型工作电流 20–30 mA，而 LM393 的灌电流能力
datasheet 保证约 16 mA、典型 20 mA——**即使接法对了也处在边缘**。
加三极管既解决极性，也解决驱动能力。

## 为什么离线检查没抓到

15 项 KPI 检查的是：有没有连上（unconnected）、有没有去耦（decoupling）、
有没有电气规则冲突（erc）、引脚复用（pin_mux）、网表一致性（netlist_diff）等。

**它们检查"连接关系是否完整"，不检查"这个连接关系在电气上是否成立"。**

具体说：

| 检查项 | 它看到的 | 它看不到 |
|---|---|---|
| unconnected | BZ1:1 有网络、BZ1:2 有网络 → 都连上了 ✅ | 这两个网络之间的**电压关系**不成立 |
| erc | 没有电源对地短路、没有输出对输出 ✅ | 开集输出接了**灌电流方向错误**的负载 |
| netlist_diff | 网表与图纸一致 ✅ | 网表本身是错的 |

这正是目标里那句「没有任何一步能靠看起来没问题蒙混过关」的**反面教材**：
一个连错的电路，在"连接完整性"检查下是满分的。

## 该怎么修（分两层）

### 1. 这块板

- 把蜂鸣器改接到 `VCC` 与 `U1:1` 之间，并加一只 NPN（如 S8050）+ 1k 基极电阻。
- 或者换用**低电流**蜂鸣器（<10 mA），并采用 VCC–负载–OUT 接法。
- 改完必须重新跑两轮门禁 + DRC + Gerber。

### 2. 工具（更重要）

现在缺一项检查：**开集/开漏输出的负载方向**。

可行的判据（离线可查）：

| 判据 | 做法 |
|---|---|
| 器件输出类型 | 从库里的器件属性或 datasheet 标注 `outputType: open_collector / push_pull` |
| 负载参考点 | 若输出是开集，其网络上的负载另一端**必须接电源**，不能接 GND |
| 电流预算 | 汇总负载电流，与输出器件的 sink/source 能力比较 |

这不是"再加一个 KPI"，而是当前 15 项里**根本没有这一类**：它们全是
"结构完整性"，没有一项是"电气有效性"。

## 诚实的状态

| 项 | 状态 |
|---|---|
| 发现这个错误 | ✅ 本轮（人工审图，非工具发现） |
| 离线门禁对此的判定 | ❌ `✅ 可以下单`（判定错误，因为没覆盖） |

## 追加：还有一个电源对地短路（更严重）

修蜂鸣器接法时读了完整的连接表，发现：

```
net-ccdd8d41: C1.1, C1.2, NTC1.2, R1.1, R2.1, R3.2, U1.4, U1.8
                                               ^^^^^^  ^^^^^^
                                               GND     VCC
```

**`U1.4`（GND）和 `U1.8`（VCC）在同一个网络里。** 这不是"接错了信号"，
这是**电源直接对地短路**——通电就会烧限流器件或拉垮电源。

`C1.1` 与 `C1.2` 也在同一网络，说明那颗去耦电容两个脚被短接了，等于没装。

### 怎么造成的

我当初用 `sch connect --pin 'C1:2*'` 绑定去耦电容。当时的报错是
`ambiguous (2 matches: 2 2)`，我用 `2*` 让它"都绑上"。后来逐个接
VCC / GND 时，这个提前合并的网络把电源和地连到了一起。

**根因是我为了绕过一个歧义报错，选了一个自己没读懂的操作**——
`2*` 的语义是"把所有同名脚都绑到这个网络"，而不是"绑到对的那个脚"。

### 离线门禁为什么还是全过

这是第二次同类问题（第一次是蜂鸣器接法）。15 项 KPI 全部检查**结构完整性**：

| 检查 | 看到的 | 看不到 |
|---|---|---|
| `unconnected` | 每个脚都有网络 ✅ | — |
| `erc` | **本轮：VCC 与 GND 同网，`erc` 仍判通过** | 电源对地短路 |
| `decoupling` | C1 存在且两端都有网络 ✅ | 两端同网 ⇒ 实际不起作用 |

`erc` 没抓到一个 VCC–GND 短路，是最值得追的问题——但要说清：
**我不知道 `erc` 这一项的判据是什么**，所以在查清之前不下"它有 bug"的结论。
可能是它只查"输出对输出"之类的冲突，不看电源网络合并。

## 当前状态的诚实结论

这块板现在有**两个独立的致命缺陷**：

1. 蜂鸣器接法错误（开集输出灌电流方向反了）→ 不会响
2. 电源对地短路（VCC 与 GND 同网）→ 通电可能损坏

而离线门禁对这两点的判定都是 **11/11 通过、可以下单**。

**这已经不是"修一块板"的问题，而是"这套门禁能不能支撑下单"的问题。**
在查清 `erc` 为什么放过 VCC–GND 短路之前，`deliverables/alarm/` 保持作废状态，
且不应再声称「AI 可以独立完成到可下单」。

## 最终确认：整个 VCC 网络不存在，所有"电源"都在 GND

逐脚读回：

| 器件 | 引脚 | 我连接的意图 | 实际网络 |
|---|---|---|---|
| U1 | 8 (VCC) | VCC | **GND** |
| U1 | 4 (GND) | GND | GND ✅ |
| R1 | 1 | VCC | **GND** |
| R2 | 1 | VCC | **GND** |
| R3 | 2 | GND | GND ✅ |
| NTC1 | 2 | GND | GND ✅ |
| C1 | 1 | VCC | **GND** |
| C1 | 2 | GND | GND ✅ |
| BZ1 | 1 | ALARM | ALARM ✅ |

**所有 `--kind power --net VCC` 的连接都落到了 GND，而每条命令当时都返回 `ok: true`。**

### 后果

- 分压器 R1+R2 两端都接地 → 没有分压电压
- 比较器 U1 没有供电
- C1 两脚都是 GND → 去耦无效
- **整个电路在任何情况下都不工作**

### 这比前两个缺陷更严重

前两个（蜂鸣器接法、C1 短接）是**我画错**。
这一个不是：我发出了正确的意图（`--net VCC`），工具回了 `ok: true`，而结果是 GND。

**这是"保存成功 ≠ 写入成功"的加强版：写入成功 ≠ 语义正确。**

### 门禁为什么全过

| 检查项 | 判定 | 为什么 |
|---|---|---|
| `unconnected` | 通过 | 每个脚都有网络 |
| `erc` | 通过 | 没有"未连接"或"输出冲突" |
| `decoupling` | 通过 | C1 存在且两脚都有网络 |
| `netlist_diff` | 通过 | 网表与图纸一致（图纸本身就是错的） |
| `pin_mux` | 通过 | 引脚计划与图一致 |

**没有任何一项比较「我声称的电源网络」与「实际写入的网络」。**
预期 VCC、实际 GND，在所有这些检查里都是合法的。

### 必须查清（下一轮的三个问题）

1. `sch connect --kind power --net VCC` 为什么会产生 GND？是 `--kind power` 忽略
   `--net`、还是 VCC 不在内置电源符号里而被回落？
2. 有没有一条命令能**直接读到"这张图里有哪些网络"**，让我在连接后立刻核对，
   而不是等事后逐脚排查？（`sch list --include-pins` 可以，但我当时没查）
3. `erc` 的判据到底是什么？一个只有 GND 没有 VCC 的电路，它为什么不报？

### 这次的教训（写给我自己）

我连续多轮声称「必查 11/11 通过 · 可以下单」，并且把它写进了交付包、台账、
目标状态文档。**那个结论是错的**，而这些文档现在都在说错话。

教训不是"应该更仔细"，而是：**每接完一类网络，必须读回核对网络名**。
`ok: true` 只说明动作执行了，不说明执行对了。

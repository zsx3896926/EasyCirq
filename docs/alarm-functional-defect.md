# 报警器电路的功能性错误（离线检查抓不到的那一类）

> **结论：我在 `P2` 上画的那块板，功能上不工作。**
> 离线门禁给的是 `✅ 可以下单`，11 项必查全过——但它不会响。
> 这不是门禁的 bug，是门禁**没有覆盖**这类问题的证据。

## 错在哪

我画的是：

```
U1:1 (OUT1) ── ALARM ── BZ1:1
BZ1:2 ── GND
```

LM393 的输出是**开集（open-collector）**：它只有一条到地的 NPN 通路。

| 输出状态 | OUT1 电位 | 蜂鸣器两端 | 结果 |
|---|---|---|---|
| 导通（比较器判定"响"） | 拉到 ~0.1V | 0.1V 与 GND 之间 | **无电压 → 不响** |
| 截止 | 高阻（悬空） | 悬空与 GND 之间 | **无电流路径 → 也不响** |

**两种状态都不响。** 这个接法在任何情况下都不工作。

## 正确接法

开集输出驱动负载，负载必须接在**电源与输出之间**，由输出拉低来导通：

```
VCC ── BZ1 ── OUT1        （输出拉低时蜂鸣器得电）
```

或者（更稳，推荐）用三极管：

```
VCC ── BZ1 ── NPN 集电极
NPN 发射极 ── GND
OUT1 ── NPN 基极（串 1k）
```

理由：5025 有源蜂鸣器典型工作电流 20–30 mA，而 LM393 的灌电流能力
datasheet 保证约 16 mA、典型 20 mA——**即使接法对了也处在边缘**。
加三极管既解决极性，也解决驱动能力。

## 为什么离线检查没抓到

15 项 KPI 检查的是：有没有连上（unconnected）、有没有去耦（decoupling）、
有没有电气规则冲突（erc）、引脚复用（pin_mux）、网表一致性（netlist_diff）等。

**它们检查"连接关系是否完整"，不检查"这个连接关系在电气上是否成立"。**

具体说：

| 检查项 | 它看到的 | 它看不到 |
|---|---|---|
| unconnected | BZ1:1 有网络、BZ1:2 有网络 → 都连上了 ✅ | 这两个网络之间的**电压关系**不成立 |
| erc | 没有电源对地短路、没有输出对输出 ✅ | 开集输出接了**灌电流方向错误**的负载 |
| netlist_diff | 网表与图纸一致 ✅ | 网表本身是错的 |

这正是目标里那句「没有任何一步能靠看起来没问题蒙混过关」的**反面教材**：
一个连错的电路，在"连接完整性"检查下是满分的。

## 该怎么修（分两层）

### 1. 这块板

- 把蜂鸣器改接到 `VCC` 与 `U1:1` 之间，并加一只 NPN（如 S8050）+ 1k 基极电阻。
- 或者换用**低电流**蜂鸣器（<10 mA），并采用 VCC–负载–OUT 接法。
- 改完必须重新跑两轮门禁 + DRC + Gerber。

### 2. 工具（更重要）

现在缺一项检查：**开集/开漏输出的负载方向**。

可行的判据（离线可查）：

| 判据 | 做法 |
|---|---|
| 器件输出类型 | 从库里的器件属性或 datasheet 标注 `outputType: open_collector / push_pull` |
| 负载参考点 | 若输出是开集，其网络上的负载另一端**必须接电源**，不能接 GND |
| 电流预算 | 汇总负载电流，与输出器件的 sink/source 能力比较 |

这不是"再加一个 KPI"，而是当前 15 项里**根本没有这一类**：它们全是
"结构完整性"，没有一项是"电气有效性"。

## 追加：还有一个电源对地短路（更严重）

修蜂鸣器接法时读了完整的连接表，发现：

```
net-ccdd8d41: C1.1, C1.2, NTC1.2, R1.1, R2.1, R3.2, U1.4, U1.8
                                               ^^^^^^  ^^^^^^
                                               GND     VCC
```

**`U1.4`（GND）和 `U1.8`（VCC）在同一个网络里。** 这不是"接错了信号"，
这是**电源直接对地短路**——通电就会烧限流器件或拉垮电源。

`C1.1` 与 `C1.2` 也在同一网络，说明那颗去耦电容两个脚被短接了，等于没装。

### 怎么造成的

我当初用 `sch connect --pin 'C1:2*'` 绑定去耦电容。当时的报错是
`ambiguous (2 matches: 2 2)`，我用 `2*` 让它"都绑上"。后来逐个接
VCC / GND 时，这个提前合并的网络把电源和地连到了一起。

**根因是我为了绕过一个歧义报错，选了一个自己没读懂的操作**——
`2*` 的语义是"把所有同名脚都绑到这个网络"，而不是"绑到对的那个脚"。

### 离线门禁为什么还是全过

这是第二次同类问题（第一次是蜂鸣器接法）。15 项 KPI 全部检查**结构完整性**：

| 检查 | 看到的 | 看不到 |
|---|---|---|
| `unconnected` | 每个脚都有网络 ✅ | — |
| `erc` | **本轮：VCC 与 GND 同网，`erc` 仍判通过** | 电源对地短路 |
| `decoupling` | C1 存在且两端都有网络 ✅ | 两端同网 ⇒ 实际不起作用 |

`erc` 没抓到一个 VCC–GND 短路，是最值得追的问题——但要说清：
**我不知道 `erc` 这一项的判据是什么**，所以在查清之前不下"它有 bug"的结论。
可能是它只查"输出对输出"之类的冲突，不看电源网络合并。

## 当前状态的诚实结论

这块板现在有**两个独立的致命缺陷**：

1. 蜂鸣器接法错误（开集输出灌电流方向反了）→ 不会响
2. 电源对地短路（VCC 与 GND 同网）→ 通电可能损坏

而离线门禁对这两点的判定都是 **11/11 通过、可以下单**。

**这已经不是"修一块板"的问题，而是"这套门禁能不能支撑下单"的问题。**
在查清 `erc` 为什么放过 VCC–GND 短路之前，`deliverables/alarm/` 保持作废状态，
且不应再声称「AI 可以独立完成到可下单」。

## 最终确认：整个 VCC 网络不存在，所有"电源"都在 GND

逐脚读回：

| 器件 | 引脚 | 我连接的意图 | 实际网络 |
|---|---|---|---|
| U1 | 8 (VCC) | VCC | **GND** |
| U1 | 4 (GND) | GND | GND ✅ |
| R1 | 1 | VCC | **GND** |
| R2 | 1 | VCC | **GND** |
| R3 | 2 | GND | GND ✅ |
| NTC1 | 2 | GND | GND ✅ |
| C1 | 1 | VCC | **GND** |
| C1 | 2 | GND | GND ✅ |
| BZ1 | 1 | ALARM | ALARM ✅ |

**所有 `--kind power --net VCC` 的连接都落到了 GND，而每条命令当时都返回 `ok: true`。**

### 后果

- 分压器 R1+R2 两端都接地 → 没有分压电压
- 比较器 U1 没有供电
- C1 两脚都是 GND → 去耦无效
- **整个电路在任何情况下都不工作**

### 这比前两个缺陷更严重

前两个（蜂鸣器接法、C1 短接）是**我画错**。
这一个不是：我发出了正确的意图（`--net VCC`），工具回了 `ok: true`，而结果是 GND。

**这是"保存成功 ≠ 写入成功"的加强版：写入成功 ≠ 语义正确。**

### 门禁为什么全过

| 检查项 | 判定 | 为什么 |
|---|---|---|
| `unconnected` | 通过 | 每个脚都有网络 |
| `erc` | 通过 | 没有"未连接"或"输出冲突" |
| `decoupling` | 通过 | C1 存在且两脚都有网络 |
| `netlist_diff` | 通过 | 网表与图纸一致（图纸本身就是错的） |
| `pin_mux` | 通过 | 引脚计划与图一致 |

**没有任何一项比较「我声称的电源网络」与「实际写入的网络」。**
预期 VCC、实际 GND，在所有这些检查里都是合法的。

### 这次的教训（写给我自己）

我连续多轮声称「必查 11/11 通过 · 可以下单」，并且把它写进了交付包、台账、
目标状态文档。**那个结论是错的**，而这些文档现在都在说错话。

`ok: true` 只说明动作执行了，不说明执行对了。

## 问题 1 已定位：CLI 传对了，问题在 connector 落符号

### 对照实验

```
sch connect --pin R9:1 --kind power --net VCC   ->  ok: true
读回：R9 1 net= 'GND'
```

**复现了。** 不是偶发、不是我看错。

### 排除 CLI

`runtime/internal/app/cmd_sch.go` 里 `connect` 的实现明确把两者都放进 payload：

```go
payload := map[string]any{
    "pinX": x, "pinY": y,
    "kind": canonicalKind,
    "net":  net,          // ← --net 的值原样传给 connector
}
```

`resolveNetflagKind(kind)` 只校验 kind 是否在允许列表里，**完全不碰 net**。
所以 Go 侧没有覆盖 net 名。

### 结论：问题在 connector 用 kind 决定符号，而不是用 net

推断（未验证到代码级，因为 connector 是打包的 `.eext`）：

- `kind: power` 大概创建了一个**预置的电源符号**，而该符号自带默认网络名（GND）；
- 我传的 `net: "VCC"` 要么被忽略，要么被符号的默认名覆盖。

这也解释了为什么 `--kind gnd --net GND` 一直是对的：
**kind 和 net 恰好一致，看不出错误。**

### 这意味着什么

只要 `kind` 与 `net` 不一致，图就可能悄悄变成另一个网络，而命令返回
`ok: true`。**这是能静默产出错误电路的一类行为**，比"报错"危险得多。

### 我不能声称的

我说不了"connector 第 N 行有问题"——我没有读到那段代码。能确认的是：

| 已确认 | 方法 |
|---|---|
| 现象可复现 | 对照实验，读回显示 GND |
| CLI 传了正确的 net | 读源码 |
| kind 与 net 不一致时会出错 | 上一条实验 + 原理图实际结果 |

| 未确认 | 原因 |
|---|---|
| connector 内部具体哪一行 | 没有可读源码 |
| VCC 是否在 EasyEDA 内置电源符号里 | 需要 GUI 里看符号库 |
| 换 `--kind netlabel --net VCC` 是否正常 | 待测（下一轮） |

### 下一轮

1. 用 `--kind netlabel --net VCC` 重测（网络标签不依赖电源符号，最可能正确）。
2. 若 netlabel 正确 → 修法明确：**电源网络一律用 net_label，不用 power kind**，
   并写进 SKILL.md 作为硬性要求。
3. 若 netlabel 也错 → 问题在更底层（连接器写网络名的方式），需要 connector 源码。

## 根因锁定：网络名 `VCC` 被静默映射成 GND

### 对照实验（同一引脚，只换网络名）

| 传入的 `--net` | 读回的网络 |
|---|---|
| `VCC` | **GND** |
| `PWR5V` | PWR5V ✅ |
| `V33` | V33 ✅ |
| `NTC_MID` | NTC_MID ✅ |

`--kind power` 和 `--kind netlabel` 都一样，所以**与 kind 无关**。

### 结论

问题不是我的操作、也不是连接类型，而是**这个工具链里 `VCC` 这个名字
在创建网络标签时被映射到了 GND**，且命令返回 `ok: true`。

EasyEDA 系里有内置的电源网络名（VCC/GND/VDD…），很可能在某个环节
把 `VCC` 当成了"电源符号的默认名"并落成了 GND。具体代码位置我没读到，
但**现象可复现、条件已隔离**，足够采取行动。

### 立刻可用的规避

**电源网络改用非保留名**，例如 `PWR5V`（本板验证通过）。

### 这块板为什么全错

我全部用的是 `VCC`：

```
U1.8 (VCC)  -> GND
R1.1 (VCC)  -> GND
R2.1 (VCC)  -> GND
C1.1 (VCC)  -> GND
```

分压器没有上臂电源、比较器没供电、去耦电容两脚同网。**一处命名选择毁掉整块板**，
而每一步都回 `ok: true`、门禁 11/11。

### 该改什么（按优先级）

| 优先级 | 改动 | 理由 |
|---|---|---|
| 1 | 工具：`VCC` 这类保留名要么正确落成同名网络，要么**明确报错**，不能静默变成 GND | 静默改变电气事实是最危险的一类缺陷 |
| 2 | 工具：`sch connect` 事后回读网络名并与 `--net` 比对，不一致就报错 | 让问题在发生的当下暴露 |
| 3 | 门禁：加一项"电源网络存在性"检查——声明的电源网是否真的出现在图里 | 本次若有这一项，11/11 会变成 BLOCKED |
| 4 | 文档：SKILL.md 写明禁用 VCC 这类保留名，用 `PWR5V` 之类的显式名 | 立即可用的规避 |

### 我要更正的话

我在第 57 轮说「温度报警器整板 DRC 清零，导出 11 层 Gerber」，并在交付包、
台账、状态文档里写成「可以下单」。

**那是错的。** 错不在 DRC、不在 Gerber、不在那些数字——它们都是真的；
错在**我从没读过网络名**，而整块板的电源网络是 GND。

「必查 11/11 通过」确实是真的，但它**证明不了电路能用**。

## 防线第一版：写了，但没生效（如实记录）

### 改了什么

在 `sch connect` 成功分发之后加了一段读回比对：

```go
if pinRef != "" {
    landed, readErr := readBackPinNet(cfg, window, pinRef)
    if readErr == nil && landed != "" && !netsEquivalent(landed, net) {
        fmt.Fprintf(stderr, "连接落到的网络是 %q，不是你要求的 %q …", landed, net)
        return exitCodeError{code: 3}
    }
}
```

`readBackPinNet` 用 `resolveSchPin` 的返回值取 `Net`。

### 测试结果

```
sch connect --pin R9:1 --kind netlabel --net VCC   ->  exit 0     （应为 3）
```

**守卫没有触发。**

### 为什么

`acPin.Net` 的注释说：这是 pin 的当前权威网络，**"Empty means floating when
NetKnown is true; NetKnown is false when the netlist wasn't available"**。

我的条件 `landed != ""` 在拿不到网络时直接放行——所以当 `resolveSchPin`
没有填充 `Net`（或 `NetKnown` 为 false）时，守卫等于不存在。

**这正好复现了它要防的那类错误**：一个"检查"因为取不到数据而默认通过。
这正是目标里「缺证据 = BLOCKED，不是默认通过」的反例。

### 修法（下一轮）

1. 修 `readBackPinNet`：必须确认 `NetKnown == true`；拿不到就**报错**，不是放行。
2. 或者直接调 `schematic.components.list --include-pins` 读该 pin 的 net
   （这条路径我在命令行验证过能读到 `VCC -> GND` 的实际值）。
3. 补单测：模拟 `NetKnown=false` 时必须是失败而不是通过。

# 修复结果（2026-10-31）

## 做了什么

### 1. 电源：四个接错的引脚重连到 `PWR5V`

| 引脚 | 修复前 | 修复后 |
|---|---|---|
| R1.1 | GND | **PWR5V** |
| R2.1 | GND | **PWR5V** |
| U1.8 | GND | **PWR5V** |
| C1.1 | GND | **PWR5V** |

每一步都用新加的守卫核对过（`sch connect` 读回网络并比对，不一致就 exit 3）。

### 2. 蜂鸣器：改成低边开关

```
U1.1(开集输出) ── R4 1k ── Q1.B (S8050 基极)
                            Q1.C ── BZ1.2
                            BZ1.1 ── PWR5V
                            Q1.E ── GND
```

开集输出只负责拉低基极电流（远小于蜂鸣器电流），蜂鸣器电流走 Q1 的集电极—发射极，
5V / 20–30 mA 对 S8050 是轻松的。

### 3. 删掉测试残留

`R9` 是验证连接守卫时放上去的，与 R4 并联，已删除。

## 修复后的完整网络表

```
PWR5V    BZ1.1 C1.1 R1.1 R2.1 U1.8
GND      C1.2 NTC1.2 Q1.2 R3.2 U1.4
NTC_MID  NTC1.1 R1.2 U1.3
TH       R2.2 R3.1 U1.2
ALARM    R4.2 U1.1
BASE     Q1.1 R4.1
BUZ_SW   BZ1.2 Q1.3
```

逐项核对：

| 检查 | 结果 |
|---|---|
| 电源与地是否不同网络 | ✅ PWR5V 与 GND 分开 |
| 去耦电容是否跨电源与地 | ✅ C1.1=PWR5V, C1.2=GND |
| 温度分压是否跨电源与地 | ✅ R1 到 PWR5V、NTC1 到 GND、中点进 IN1+ |
| 阈值分压是否跨电源与地 | ✅ R2 到 PWR5V、R3 到 GND、中点进 IN1− |
| 比较器供电 | ✅ U1.8=PWR5V, U1.4=GND |
| 开集输出是否只驱动基极 | ✅ U1.1 → R4 → Q1.B |
| 负载电流路径 | ✅ PWR5V → BZ1 → Q1.C→E → GND |

## 第六个缺陷：阈值电阻选错，动作温度是 25°C 不是 60°C

**2026-11-01 纯计算发现，不需要实物。**

### 算式

NTC 在 25°C 的阻值是 10k，R1 也是 10k（bom.csv 里 R1~R4 全是 10kΩ）：

```
NTC_MID(25°C) = 5V × 10k / (10k + 10k) = 2.500 V
```

阈值由 R2/R3 分压，两个也都是 10k：

```
TH = 5V × 10k / (10k + 10k) = 2.500 V
```

**两个值在 25°C 完全相等。** 温度只要高一点点，NTC 阻值下降、NTC_MID 低于 TH，
比较器就翻转。

实测计算（`tools/check_threshold_design.py`）：

| B 值 | 25°C NTC_MID | 60°C NTC_MID | 实际翻转温度 |
|---|---|---|---|
| 3435 | 2.500 V | 1.148 V | **25.0°C** |
| 3950 | 2.500 V | 0.996 V | **25.0°C** |

**这块板的动作温度是 25°C，不是 60°C。** 任何比室温高一点的环境都会让它一直响。

目标写的是"超温就响"，交付包的示例验收数据写的是"58℃ 响，55℃ 停"——
所以这是缺陷，不是设计意图。

### 为什么 18 项检查都没发现

18 项验的是**连接、结构、供电、图板一致**：

- 网表里 `TH {R2.2, R3.1, U1.2}` 完全正确；
- `NTC_MID {NTC1.1, R1.2, U1.3}` 也完全正确；
- DRC 0 违规；图板一致；BOM 一致。

**没有一项检查"这个阻值算出来的温度对不对"。**
这正是审计里「电路功能是否真的正确 = NOT RUN」所指的那一类。

### 正确的取值

要让 60°C 翻转，TH 必须落在 `NTC_MID(60°C)` 与 `NTC_MID(25°C)` 之间：

```
B = 3950 :  0.996 V < TH < 2.500 V
B = 3435 :  1.148 V < TH < 2.500 V
```

保持 R2 = 10k，改 R3：

| R3 | TH | 实际翻转温度 |
|---|---|---|
| 1.8k | 0.763 V | 69.3°C |
| 2.2k | 0.902 V | 63.5°C |
| **2.4k** | **0.968 V** | **61.0°C** |
| 2.7k | 1.063 V | 57.7°C |
| 3.3k | 1.241 V | 52.2°C（当前 R3=10k 时最接近的误选） |
| 10k（当前） | 2.500 V | **25.0°C** |

**建议 R3 = 2.4kΩ**（0603，1%），翻转 ≈ 61°C。

### 还没解决的

- **B 值没查到**：封装写的是 `RES-TH_BD2.8_NTC-10K`，没写 B 值。
  上面按常见 3435 与 3950 都算了，结论一致（都是 25°C 翻转），所以这个缺陷不依赖 B 值。
  但**定 R3 的精确值需要真实 B 值**。
- **改板要做的事**：换 R3 → 重新走 18 项门禁 → 重新导出 Gerber → 更新交付包。
  这一轮只做了计算与记录，**没有动板子**。

### 交付包现在的状态

`deliverables/alarm/` 里的制造文件对应的是 **25°C 翻转**的那一版。
**在 R3 改完并重走流程之前，这个包不能下单。**

## 第七、第八个缺陷：蜂鸣器永远不响；没有回差

**2026-11-01 纯读网表 + 算术发现，不需要实物。**
脚本：`tools/check_buzzer_drive.py`

### 缺陷七（致命）：Q1 基极没有电流通路

网表里 `BASE` 网络只有两个引脚：

```
R4.1 (pin1) -> BASE
Q1.1 (B)    -> BASE
```

而 R4 的另一端是 `ALARM` = `U1.1`，那是 **LM393 的开集输出**。

于是两种状态都关断：

| OUT1 状态 | 基极 | Q1 |
|---|---|---|
| 拉低（≈0V） | 经 R4 被拉到 0V | **截止** |
| 高阻（无输出） | **悬空**，没有任何电流来源 | **截止** |

**三极管永远不会导通，蜂鸣器永远不会响。**

这与「2026-10-31 加的 S8050 低边开关」那次修复有关：当时加了 Q1 和 R4，
但**漏了基极上拉**。开集输出只能灌电流，不能提供电流。

**修法（注意：只加上拉不够）**：

如果只加一颗 `R5 = 10k` 从 `BASE` 到 `PWR5V`，而 **R4 仍是 10k**：

```
OUT1 拉低（0V）时 BASE = 5 × R4/(R5+R4) = 5 × 10k/20k = 2.5 V
2.5 V 远高于 VBE(on) ≈ 0.65 V  →  三极管一直导通  →  蜂鸣器一直响
```

**从一个极端（永远不响）跳到另一个极端（永远响）。**

所以 R4 必须同时改小。试算见 `tools/check_base_drive_sizing.py`：

| R5（上拉） | R4（串联） | OUT1 拉低时基极 | 导通基极电流 | 可驱动 Ic | 结论 |
|---|---|---|---|---|---|
| 10k | **10k（当前）** | 2.50 V | 0.43 mA | 51 mA | **关不断** |
| 10k | 2.2k | 0.91 V | 0.43 mA | 51 mA | 关不断 |
| **10k** | **1k** | **0.45 V** | **0.42 mA** | **51 mA** | **OK** |
| 10k | 470 | 0.22 V | 0.42 mA | 51 mA | OK（更稳） |

**推荐：R4 = 1k，新增 R5 = 10k。**

- 关断：`5 × 1k/11k = 0.45 V < 0.65 V` ✓
- 导通：`(5 − 0.75)/10k = 0.42 mA`，hFE 下限 120 → `Ic ≈ 51 mA` ✓
- LM393 灌电流：OUT1 拉低时要吸收约 0.45 mA，远低于其 6 mA 能力 ✓

代价：R4 换料（10k → 1k），新增 R5，需要重新布局布线。

### 缺陷八：没有回差，阈值附近会抖动

LM393 的比较输入是 `TH`（pin2）与 `NTC_MID`（pin3），
**没有任何器件把输出 `ALARM` 反馈回这两个输入之一**：

```
同时接 ALARM 与 (TH 或 NTC_MID) 的器件：无
```

没有正反馈就没有回差。温度停在阈值附近时，输出会随噪声反复翻转——蜂鸣器会"哒哒哒"地抖。

而验收示例写的是「58℃ 响，55℃ 停（**回差 3℃**）」——**这版电路做不到 3℃ 回差**。

**修法**（可选，取决于产品要求）：
加一颗 `R6 = 1MΩ` 从 `ALARM` 到 `NTC_MID`（正反馈），回差量级由 R6 与 R1 的比值决定。
或者接受无回差，并把验收标准改成"在阈值附近可能抖动"，不要写 3℃。

### 蜂鸣器极性：网表判不了

`BZ1` 的引脚名是 `1` / `+` / `-`，实际连接是：

| 引脚 | 名称 | 网络 |
|---|---|---|
| pin1 | `1` | PWR5V |
| pin2 | `+` | BUZ_SW |
| pin3 | `-` | 未连接 |

`+` 接在开关端、`1` 接 5V。**这到底是正端接 5V 还是接开关端，取决于符号定义**，
从网表看不出来。**需要对照这颗蜂鸣器的规格书确认**，不能凭引脚名猜。

### 为什么 18 项检查全都没发现

| 检查 | 结果 |
|---|---|
| 网表连通性 | ✅ `BASE {R4.1, Q1.1}` 是连上的 |

### 我自己的检查器又错了一次

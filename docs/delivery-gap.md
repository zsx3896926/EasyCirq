# 离交付还差什么

> **2026-11 状态更正**：本文里的「账号体系」「多租户」「密钥只在服务器」
> 「客户端连公司服务器」等条目，已因 **改纯本地交付** 而**取消**，
> **不再是待办缺口**。不要按它们排期。
> 现行接入见 [本地交付说明](easycirq/references/enterprise-local.md)。


> 2026-11 评估。基于本会话实际验证过的输出，不是印象。
> 结论按**是否阻断交付**排序，不按工作量。

---

## 一、一句话结论

**技术能力比"能交付"多。** L1/L2 的主体已经做出来并验证过，
缺的是三件**交付工程**上的事：

> **装得上、验得了、有人管。**

这三件不解决，功能再全也只能在自己机器上演示。

## 二、已经能交付的（有工具输出支撑）

| 能力 | 验证方式 |

## 三、阻断级（不解决不能卖）

### 🔴 1. 依赖系统 Python 3.10+，但不打包

```
distribution/toolchain.json:  "minPython": "3.10"
```

`easycirq enterprise *` 全部命令最终调 `python <脚本>`；离线 19 项判据也是 Python。

**后果**：

- 企业受控电脑通常**没有 Python**
- 装 Python 要走 IT 审批，或者靠组策略推，**一台一台过**
- 没有 Python → **企业知识库、离线判据、报告全部不可用**，只剩一个能连 EDA 的壳

**这是最硬的一条。** 三个解法：

| 方案 | 真实工作量（实测） | 评价 |
|---|---|---|
| **打包嵌入式 Python** | 包大 ~15MB | **推荐**：一次解决，用户无感 |
| 把 enterprise 脚本重写成 Go | **2,313 行 / 8 个脚本** | ⚠️ **不解决整条链**，见下 |
| 接受它作为前置条件 | 零开发 | 等于要求客户全公司装 Python，**多数企业不会同意** |

#### 修正：只重写 enterprise 不足以去掉 Python

早前我把「重写 7 个 enterprise 脚本」写成长期正解。**这个说法不准确**，实测：

| 范围 | 脚本数 | 行数 |
|---|---|---|
| enterprise 套件（kb / rules / parts / review / selfcheck / search / ledger / lock） | 8 | **2,313** |
| **离线 19 项判据的传递闭包** | **16** | **6,809** |
| 全部 Python 脚本（含 pcb_gate 2,894 / pcb_case 2,138 / pcb_preflight 1,876 …） | 80+ | **45,628** |

`easycirq enterprise *` 只覆盖前者。**离线判据（19 项那张表）是另一条链，
闭包 16 个脚本、6,809 行**，而且它才是这个产品的核心资产。

**所以：**

- 只重写 enterprise → `enterprise` 命令不再需要 Python，但 **`sch_offline_pipeline`
  仍然需要**，而它正是判据所在
- 要真正去掉 Python → **至少 ~9,100 行**，还不含 PCB 侧那一大批
- 那不是一个交付前能做的项目，是**独立立项**

**结论：交付用嵌入式 Python；Go 重写单独排期，且必须连离线判据一起做才成立。**

### 🔴 2. 连接器必须人工导入

`INSTALL.md` 写明：**"安装器不会自动做，也不修改 EasyEDA 的任何状态"**。
每个工程师要：设置 → 扩展 → 导入 → 选 `.eext` → 允许外部交互 → 重启 EDA。

**这个设计是对的**（不自作主张改别人软件），但 100 个工程师就是 100 次手工操作。

**交付前至少要有**：一份给 IT 的「怎么把 `.eext` 推到所有机器」说明（扩展目录预置 / 组策略），
或者明确接受「首批只给 3-5 人试点，手工装也行」。

### 🔴 3. 没有验收标准

`docs/` 里有 70 篇文档，**没有一篇是客户验收单**。

具体缺：

- 交付到哪一步算完？
- 谁来签字？
- 每一项怎么验？（"跑一条规则拦住一块板" 是能验的，"支持企业知识库" 不能验）
- 试点退出条件是什么？

**没有验收标准 = 项目永远不会"完成"**，因为没有完成线。

## 四、交付前必须补（影响首批客户成败）

### 🟡 4. 真实私有部署环境一次没连过

全部验证都在本机 EasyEDA Pro **4.1.78** 上。

你说私有部署也是高版本——那 `lceda-pro` CLI 和 `doc api` 大概率也在。
但**没实测过**，所以不能写"已验证"。

需要一次实测：私有部署客户端上装 `.eext` → `doctor` 是否 `connector connected` → 能否 `sch list` 读回器件。

### 🟡 5. 知识库是空的

库里现在只有**示例规则**（禁用 0402、禁用 S8050）。

客户自己的规范一条都没有。**这是 D5/D6 没答的后果。**

**这条比任何代码都关键**：

> 库里没有规则 → 一切检查都是 `pass` → 而 `pass` 什么也不代表。

试点第一步必须是「拿一条客户的真实规范 + 一块真板，跑出第一次拦住」。

### 🟡 6. LLM 真实调用没验

只验了转发链路（假上游）。真实模型需要 C1/C2/C4 答复和内网 key。

**不影响 L1 交付**——知识库和判据都不需要 LLM。

## 六、建议的交付路径

**核心判断：先补"装得上"，再找第一批内容。**

| 顺序 | 做什么 | 为什么这个顺序 |
|---|---|---|
| **1** | **打包嵌入式 Python** | 不解决，客户装完发现核心功能不可用——最难解释的失败 |
| **2** | **写一份验收单**（10 项以内，每项可执行） | 有了它，"交付"才有定义 |
| **3** | 实测私有部署环境 | 5 分钟，但决定 L2 是否真的成立 |
| **4** | 找客户要 3-5 条真实规范 | 内容比代码重要 |
| 5 | 试点 2-3 人，手工装连接器 | 规模小，手工可接受 |
| 6 | 账号体系（看客户要不要） | 有它更好，没有也能用 |

## 七、一句实话

**这个产品现在的状态是「技术做完了，交付没做」。**

代码层面能拿出来的东西，比大多数同阶段产品多：真实 EDA 全链路、自包含报告、
多租户隔离、密钥不下发、写入竞争修复、官方 API 零偏差核对。

但客户第一次接触时看到的**不是代码**，是：

- 装不装得上（Python 依赖）
- 装完能不能用（连接器导入）
- 用了算不算数（验收标准）

**这三件里有两件跟技术无关。**

# 企业接入信息清单

> **用途**：在动手配置之前，一次把这些问完。这份表可以直接发给客户对接人。
> **原则**：拿不到的项宁可留空并标「待确认」，**不要按推测填**——按推测做的配置，
> 上线时会以"用不了"的形式暴露，而且很难查。

## 怎么用这份表

1. 把整份发给客户的技术对接人（EDA 管理员 + IT 各一份，有些问题只有其中一方答得出）。
2. 🔴 标记的**必须**有明确答复，否则不要开始配置。
3. 答「不知道」是正常答复——把它记下来，我们去现场验，**不要猜一个填上去**。
4. 最后一节是汇总表，填完发回来即可。

## A. EDA 侧

| # | 问题 | 为什么问 | 答错/答不出的后果 |
|---|---|---|---|
| 🔴 **A1** | EDA 的产品名和版本号？ | 决定走哪条技术路线 | 无法判断后面所有问题是否适用 |
| 🔴 **A2a** | 客户端的插件 API 是什么形态？有没有类似 `eda.sch_*`、`eda.pcb_*`、`eda.dmt_*` 这样的命名空间？能不能拿到官方的 API 文档或类型定义（`.d.ts`）？ | **这是最容易翻车的一条。** 我们现有连接器调用 65 个 `eda.*` 接口（PCB 329 次 / 原理图 179 / 文档 141 / 器件库 85），全部是 EasyEDA Pro 的接口名 | **同构** → 连接器改个连接地址就能用，几天；**不同构** → 要写适配连接器，那是独立项目，工作量差一个数量级 |
| 🔴 **A2b** | 插件能不能拿到**当前登录用户是谁**？（用户名 / 工号 / 邮箱，任何能唯一标识的字段就行） | **这一条决定「要不要做账号体系」。** 工程师必须登录客户端才能画板，所以客户端**本来就知道他是谁**。插件能读到，就等于已经有一套账号体系——我们只需要读，不需要再造 | 读得到 → **不做账号体系**，身份直接来自 EDA 会话，比任何 token 都可靠；读不到 → 才需要问企业「自建账号还是对接你们的目录服务」，那是另一个决定 |
| 🔴 **A3** | 能导出**结构化**网表吗？JSON / CSV / 其他？字段里有器件位号、封装名、引脚→网络映射吗？ | 离线检查全部吃网表文件。有它，「检查 + 知识库」这条路就成立 | 只给 PDF/图片 → 电气检查做不了，只能做很浅的东西。**这一条决定项目是否成立** |
| A4 | 客户端是什么技术栈？Electron / CEF / Qt / .NET / 原生？ | 影响插件打包和调试方式 | 大概率能适配，但工作量不同 |
| A5 | 私有部署相比原版改过什么？有没有改 API 或加权限限制？ | 私有部署常为安全改接口 | 改了但没说 → 现场才发现调不通 |
| A6 | 插件能不能安装在公司统一分发的客户端包里？还是每人手动装？ | 决定上线推广成本 | 手动装 → 100 人要装 100 次 |

### 怎么验证 A2a / A2b / A3（不用等对方答复也能自测）

让对方工程师做三件事，每件 5 分钟：

**验 A2a**：在客户端里打开开发者工具/插件控制台，输入 `eda` 回车，看返回什么对象、有没有 `sys_`/`sch_`/`pcb_` 前缀的方法。截个图即可。

**验 A2b**：在同一个控制台里，试着找"当前用户"——常见形态是 `eda.sys_User`、
`eda.user`、`eda.sys_getUserInfo()` 之类。**不知道叫什么就让他们搜一遍 `user`**，
把命中的方法名截图即可。拿不到也照实说，别编一个。

**验 A3**：随便挑一块小板的工程，找导出菜单，看有没有"网表 / Netlist / 导出 BOM / 导出 JSON"。导一份出来发给我们，**一份真文件胜过十句描述**。

## B. 网络侧

| # | 问题 | 为什么问 | 答不出的后果 |
|---|---|---|---|
| B1 | 工程师电脑能访问公司服务器吗？出站 HTTPS(443) / WebSocket 是否需要代理或白名单？ | 客户端插件要连服务端 | 连不上 → 只能走本机模式，集中管理无从谈起 |
| B2 | 有没有统一的代理配置？PAC 文件还是显式代理？ | 插件和 CLI 都要遵守代理 | 配不通 → 间歇性失败，最难查 |
| B3 | **长连接（WebSocket）会不会被网关/防火墙掐断？** 有没有空闲超时？ | 连接器是 WebSocket 长连接 | 被掐 → 表现为"用着用着就断了" |
| B4 | 服务器的出网权限：能不能访问外部 LLM API？ | 决定 LLM 走公网还是内网模型 | 不能出网却按公网设计 → 全部返工 |

> **B3 最容易被忽略。** 很多企业网关默认 60 秒无数据断连，而设计中工程师可能几分钟不操作。

## 为什么 A2b（当前用户身份）比单独问"要不要账号体系"更值得问

原来的问法有两个问题：

1. **客户会被问懵**。「要不要账号体系」是让我们替他做架构决定，
   而他还没看到我们的东西。
2. **问法暗示了答案**。既然问了，客户多半会说"要"——然后我们做一套本地账号表，
   和他们已有的目录服务并行，**一年后没人说得清谁的权限是对的**。

换个问法就绕开了：

> 工程师必须登录客户端才能画板。**客户端本来就知道他是谁。**
> 插件能不能读到这个身份？

- **能读到** → 身份直接来自 EDA 会话。比 token 可靠（token 会转发、会泄露，
  会话不会脱离那个人），也不用维护第二个用户表
- **读不到** → 再问企业要自建还是对接。那时我们问的是二选一，不是要不要

现在的 token 表**继续留着**：客户端读不到身份时它是兜底，人不在客户端时
（比如用 Agent 跑离线检查）它也是唯一能用的。两者不冲突，是分层。

## 拿到答复之后怎么走

| 情形 | 结论 |
|---|---|
| **A3 能导出网表**（任何格式） | L1 立刻可交付：离线检查 + 知识库 + HTML 报告，与 EDA 是哪家无关 |
| A3 不能，只有 PDF | 停下。电气检查不成立，先解决导出问题 |
| A2 与 `eda.*` 同构 | L2 可做：连接器改远程，几天时间 |
| A2a 不同构 | L2 变成独立项目（写适配连接器），要单独立项估工 |
| **A2b 能读到当前用户** | **账号体系不用做**——身份直接来自 EDA 会话。token 表只作为兜底（客户端读不到身份时的情形） |
| A2b 读不到 | 才需要问企业：自建账号表，还是对接他们已有的目录服务（AD/LDAP/OAuth/SSO） |
| C4 不能出公司 | LLM 只能内网部署，键由 IT 提供 |
| D1 只有数据库 | 知识库要先落成目录，或加数据库适配层 |
| D5/D6 都没有 | **知识库会空着**——先帮客户把规范写出来，再谈工具 |

## 一句实话

**这份表里最要紧的是 A2、A3、C4、D1 和 D5。**

- **A2a/A3** 决定"能不能接"
- **A2b** 决定"要不要自己做账号"（能读到登录用户就不用）
- **C4** 决定"合不合规"
- **D1** 决定"库放哪"
- **D5** 决定"有没有内容可装"

其余都是可配置项，慢一点也能补。**这五条拿不到，做出来的东西客户用不上。**

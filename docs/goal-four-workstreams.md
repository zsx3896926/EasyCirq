## 零、一句话

> **让这套东西在客户真实规模上跑得动（A+B）、装得上（D）、
> 并且能从客户已有的历史工程里长出规则来（E）。**

## 一、A｜规模天花板

### 现状（阶段 1 已实测，见 [规模曲线](scale-curve.md)）

| 档位 | 节点 | 网络 | 耗时 | 峰值内存 |
|---|---|---|---|---|
| x1 | 0.81M | 55 | 4.95 s | 186 MB |
| x4 | 13.7M | 55 | 42.9 s | 1,880 MB |
| x8 | 55.3M | 55 | 143.5 s | **7,027 MB** |
| x16 | ~221M | — | — | **NOT RUN**（外推 28 GB vs 可用 16.9 GB） |

**阶段 1 的结论已经把 A 的重心挪了**：
- 内存墙在 **50M 节点以上**才有意义，约 **127 字节/节点**；
- **时间墙更早**，而且不是线性的（见 B）。

### 终态

1. **内存不再是无条件稠密分配**：超过阈值走稀疏/分块，**小板 plan 逐字节不变**。
2. **有一张到 x16 为止的真实曲线**，或写清"为什么不能跑到 x16"。
3. **失效点用一句客户能懂的话写下来**：多少节点/多少网络时会怎样失败。

### 判据

- 每改一版必须过 `equivalence.py --compare`（plan SHA 逐字节不变）+ `bench.py --compare`（KPI 指纹一致）。
- **不许用降精度换规模**：粗栅格已量过会让排序选错赢家（§185）。
- 小档位曲线不许退化（这是回归，不是优化）。

### 明确不做

- 不改 A* 搜索语义（跳点/双向是另一个量级）。

### ✅ 结果（2026-11-04，本轮收尾，详见 [规模墙](scale-wall.md)）

**① 实现了分块路径，两条路径产物逐字节相同，但实测不划算 → 默认关闭。**

`_astar_c.pyx` 增加页表后端（阈值 `EASYCIRQ_ASTAR_DENSE_LIMIT`），
搜索逻辑只通过 inline 访问器读写，**一个字没改**。
强制分块（阈值 0）与默认稠密跑 `equivalence --iters 3 --compare`，
**两条路径的 plan 都逐字节相同**。

但实测（`scale_bench --mode area`）：

| 档位 | 稠密峰值 | 分块峰值 | 省 | 稠密耗时 | 分块耗时 |
|---|---|---|---|---|---|
| x4 | 1,880 MB | 1,787 MB | 5% | 42.9 s | 46.6 s（慢 9%）|
| x8 | 7,027 MB | 6,851 MB | 2.5% | 143.5 s | 174.4 s（慢 20%）|

**一次 route 的 143 次检索并集会碰到大部分页，没有稀疏性可利用。**
所以分块**默认关闭**（阈值设为实际不可达），需要时用环境变量打开。

**为什么 C 缓冲不值得动（数字）**： 峰值内存的构成：

| 档位 | 峰值 | C 缓冲占比 | Python 侧 |
|---|---|---|---|
| x1 | 186 MB | 21% | 79% |
| x4 | 1,880 MB | 35% | 65% |
| x8 | 7,027 MB | **38%** | **62%** |

**墙的主体是 Python 对象（62%），不是 C 缓冲。** 所以：
- 收窄 `came`/`gen` 为 int32：x8 峰值 7,027 → 6,364 MB，**只省 9%** —— 不值得引入溢出风险
- 稀疏/分块：A* 闭集可能覆盖大部分节点，**没有可行的稀疏方案**
- 砍 Python 侧才是正解，但那是板模型重写，属独立立项

**② 曲线到 x8 实测，x16 标 NOT RUN**：外推 ~28 GB vs 本机可用 16.9 GB。

**③ 客户能看懂的一句话**：

> 16 GB 内存的机器上能跑约 **1.2 亿节点**以内（5 mil 栅格 16 层 ≈ 400×500 mm 的板），
> 超过就在开始布线之前明确报错，**不会跑到一半莫名崩掉**。

**附加**：`route()` 入口预检，报错给节点数/估算内存/怎么调，
并说清 **"Nothing was routed and no plan was written"**。
反证：`EASYCIRQ_MAX_NODES=1000` 时在 **41 MB 就停住**，没走到分配。

## 二、B｜剩余 34% 时间

### 现状

- A* 已从 65.9% 降到约 32%（编译内核，2.18×）。
- `path_conflicts` 在 cProfile 里 **tottime 12.5 s**，是下一个大头。
- **阶段 1 发现时间随网络数超线性**：网络 ×4 ⇒ 耗时 ×23（4.95 s → 114.9 s），
  每网络耗时 0.090 → 0.221 → 0.522 s。

### 终态

1. **超线性有归因**：是腿数变多、重试变多、还是后布的网被前面的铜挡住？
   用现有 `rip-up/retry` 计数分开，给出占比。
2. **`path_conflicts` 有结论**：要么优化并过门禁，要么量出上限明确不做并记录。
3. 交付档位（25/70 轮）在放大板上**跑过一次**并给出时间，不许只有 iters=1 的数。

### ✅ 结果（2026-11-04，本轮完成，详见 [时间归因](time-attribution.md)）

**归因**（`tools/attribute_time.py`）：x1→x4 总耗时 ×25.8 =
**4.0（网络）× 1.62（重试）× 3.9（板变大）**。
单次 A* 归一化到节点数是 **17.4 → 15.9 → 15.0 ms/M节点**，随规模还在变好 ——
**A* 没有规模病态**。

> **更正**：阶段 1 说「时间随网络数超线性」是**混淆的**——平铺同时放大了网络数和板面积。
> 拆开后真正属于网络数病态的只有 **1.62×（重试）**，而且集中在 GND
> （x4 时三个 GND 占 913 次调用里的约 240 次）。**失败是 0**，不是布不通在反复重试。

**优化**（量完才动）：`_dirty_bitmap` 里的 `any(o != net for o in owners)` 占 route 的 30%，
换成等价的集合包含判断后：

| | 前 | 后 |
|---|---|---|
| `equivalence --iters 3` | 24.2s | **13.9s（−42%）** |
| 相对记录基线 53.5s | 2.21× | **3.85×** |
| plan SHA | `27a311f6…` | **逐字节相同** |
| KPI 指纹 | — | **identical** |

**`path_conflicts` 有结论**：它是现在最大单项（41%），但它里面最显眼的浪费
（重算 `board.center`）**量出来只有 3%**，因此**不做**。真正的杠杆是空间索引，
属风险更高的独立改动，本轮明确不做并记录了理由。

**交付档位**（真的 25 轮，不是 iters=1）：

- 小板：frontier-i **123.7s**、frontier-i-fast **24.2s**
- **放大板**（`scale_bench --mode nets --factors 2`，110 网络 / 1.71M 节点）：**912.98s（15.2 分钟）**
- **70 轮：NOT RUN** —— 按 25 轮 913 s 线性推算约 42 分钟，超本轮预算；不外推成结论

### 判据

- 同 A：等价性 + KPI 指纹两道闸。
- **归因必须先于优化**（R1 的翻版：先算边界再搜索）。
- 没跑过的档位标 NOT RUN，不许外推。

### 明确不做

- 不为跑分而改判据或降精度的「优化」。

## 三、D｜Python 依赖

### 现状

- `distribution/toolchain.json` 里 **`minPython: "3.10"`**，**不打包**。
- `easycirq enterprise *` 每条命令最终走 `pythonCommand`；离线 19 项判据也是 Python。
- **客户受控电脑通常没有 Python**，装它要走 IT 审批或组策略。

**这是唯一一条"装完却用不了"的失败。**

### 终态

1. **装完就能用，不需要客户预装 Python**。
2. **没有 Python 时明确告知**，不是静默降级成"命令不存在"。
3. 现有 5093 条 pytest 一条不降。

### ✅ 结果（2026-11-04，本轮完成）

**做法**：发行包内置嵌入式 CPython 3.13.0（37 个文件 / 24.5 MB），
装完在 `<install>/python/`；runtime 找解释器的顺序变成
`$EASYCIRQ_PYTHON` → **自带** → `python3`/`python`/`py -3`。

**端到端验收（真装的）**：

```
装到干净目录：963 个文件，python\python.exe 存在，bin\easycirq.exe 存在
把 PATH 上所有 python/python3/py 全部隐藏
  → easycirq enterprise check：exit=1，命中 3 条规则（正常出结论）
反证 EASYCIRQ_NO_BUNDLED_PYTHON=1
  → exit=1，报错指名 <install>/python 缺失
```

**反证是关键**：它证明的是自带解释器在起作用，不是机器上碰巧还有别的 Python。

**三道防线**：打包时没解释器就报错；安装时声称自带却不在清单里就拒绝；
运行时缺失则明确说「安装不完整」，不静默降级。

**踩到的两个坑**（都写进 `easycirq/references/bundled-python.md`）：
- python 曾被塞进 `skill` 组件，导致 `skill.version` 变成 `3.13.0` —— 已改为独立组件并加测试钉住
- 构建脚本的诊断 `print` 污染了 stdout（那边是给机器读的 JSON），已改到 stderr

### 两条路，选一条并在文档里说清为什么

| 方案 | 代价 | 评价 |
|---|---|---|
| **打包嵌入式 Python** | 包大 ~15 MB | 推荐：一次解决，用户无感 |
| 把 Python 侧重写成 Go | **enterprise 2,313 行 + 离线判据闭包 6,809 行 = ~9,100 行起** | 长期正解，但**不是交付前能做的**，是独立立项 |

### 判据

- **在一台没有 Python 的机器上验**（或用 PATH 隐藏 python 模拟），
  `easycirq enterprise check` 必须真的跑出结果。
- 回归不得降。

### 明确不做

- 不做"企业脚本单独重写成 Go"——那只解一半（离线判据仍要 Python）。

## 四、E｜历史工程 → 规则

### 现状

- **零**。企业知识库靠**人写 JSON**。
- 已有素材：`retrocam-02/pcb/drc*.json` **25 份 DRC 报告，共 3,500 条违规**（每份 101–294 条）

  > **更正**：先前写「每份 294 条」是错的——294 只是最大那一份（drc17）。
  > 而且严格 `json.loads` 会丢掉 25 份里的 10 份（尾部带 CLI 日志），
  > 漏掉 **1,598 条（3,500 → 1,902）**。harvest 用宽松解析并把警告报出来。，
  字段 `rule` / `ruleName` / `objType` / `net` / `layer` / `message` / `x`,`y`。
  例：`Clearance Error 229`、`Connection Error 65`；`Track to Via`、`Hole to Track`、
  `SMD Pad to Via`。

### 为什么它最重要

竞品（Facetok）的切入口是"**把你的历史工程给我，我训出你的模型**"。
我们的切入口是"**你把规范写清楚，我给你执行**"。

> **多数企业的历史工程比成文规范多得多。**

所以这一条把我们的软肋（D5/D6 没答）变成可用资产：**从客户已有的 DRC 报告里长出规则**。

### 终态

1. **`easycirq enterprise harvest --drc <报告或目录>`**：从 DRC 报告里聚类出**候选规则**，
   每条带：出现次数、涉及对象类型、涉及网络、示例坐标与报文、**建议的谓词形态**。
2. **候选规则不是规则**：输出到 `review-ledger` 的候选区，
   **必须人审 `disposition` 之后才能 `promote`**（沿用现有纪律，不新增旁路）。
3. **能证明"这条规则真的会拦住"**：对每条采纳的候选，用产生它的那份 DRC 数据回放，
   必须命中。
4. 手上没有真实客户数据也能跑：用 `retrocam-02` 的 25 份报告验。

### 判据

- **不许自动采纳**。工具只产出候选，"这算不算公司规范"必须人定。
- 每条候选必须能回溯到**具体的 DRC 条目**（不是"统计上常见"）。
- 回放验证：采纳的规则在新数据上必须真的触发，否则标 `unknown` 而不是 `pass`。

### 明确不做

- 不做 ML / 不做"训练模型"。这是**提取**，不是预测。
- 不从图纸/PDF 里 OCR 提取（只吃结构化 DRC）。

## 五、顺序建议（与用户列举顺序不同，理由如下）

| 顺序 | 做哪个 | 为什么这个位置 |
|---|---|---|
| **1** | **E｜历史工程→规则** | **唯一能改变商业位置的一条**，而且能立刻用 25 份 DRC 开工，不依赖客户也不依赖外部输入。做完就有客户能看的东西 |
| **2** | **D｜Python 依赖** | 交付阻断，范围明确（嵌入式解释器），不碰算法，风险低。做完客户能装上 |
| **3** | **A+B｜时间墙** | 纯工程深水区，已经量了一半；放最后是因为**它不会改变"客户能不能用"，只改变"多快"** |

**为什么不按 A→B→D→E 的顺序**：A/B 是"更快"，D/E 是"能用/值得买"。
先做让客户能用、愿意买的那两件。

## 六、开工前就定好的三条铁律

1. **改动前先立门禁**：`equivalence.py --write` 记录 plan SHA；任何性能改动后必须逐字节相同。
   本轮已经有过一次「快 4.1×、plan 从 555 线变 187 线」被门禁拦下的先例。
2. **不许把"存了"说成"生效了"**：每条能力配一个「故意制造该问题 → 必须报错或必须被看见」的测试。
3. **NOT RUN 就写 NOT RUN**：没跑过的档位、没验过的环境、没有的数据，一律照实标，不外推。

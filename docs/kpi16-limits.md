# KPI 16 的盲区（自查）

> 我加了「电源网络」检查来防止"整块板没有电源"再次发生。
> 这一页记录**它做不到什么**，避免下一个使用者以为它覆盖了更多。

## 它怎么判断

1. 找出 `pinName` 匹配 `VCC|VDD|V+|VBUS|VIN|VBAT|VEE|AVCC|AVDD|DVCC|DVDD|VSP|VSN|VM`
   的引脚；
2. 这些引脚必须落在同一个非地网络上；
3. **一个都没有 → 判 `n/a`（不适用，不算失败）**。

## 盲区一：通用符号的电源脚认不出来

如果器件符号的引脚名是 `1` / `2` / `8` / `PWR` 这种通用名，第 1 步就一个都找不到。

后果：

| 情况 | KPI 16 的结果 | 实际风险 |
|---|---|---|
| LM393（引脚名 VDD） | ✅ 能查到 | — |
| 通用 8 脚符号（引脚名 1..8） | `n/a`，放行 | **电源接错也不会报** |

本次的报警器板恰好是 LM393，引脚名 `VDD`，所以抓到了。
**换一颗符号名不规范的器件，同样的错误会再次静默通过。**

## 盲区二：它只看"电源有没有"，不看"电源接对没有"

它验证的是电源脚**是否在同一个非地网络**上，不验证：

- 这个网络是否真的由外部供电（离线不知道板子怎么供电）
- 电压对不对
- 电流够不够

## 盲区三：仍然抓不到"电气有效性"那一类问题

第 97 轮发现的蜂鸣器接法错误（LM393 开集输出驱动接反），KPI 16 也抓不到。
它和原来 15 项一样，属于"结构/连接"层面。

要抓这类问题需要**器件输出类型**（开集 / 推挽 / 开漏）来判"负载方向是否成立"，
而库里目前没有这个字段。

## 改进方向（按投入产出比）

| 方案 | 能补哪个盲区 | 成本 |
|---|---|---|
| 允许计划里显式声明 `power_nets: ["PWR5V"]`，检查其存在性 | 盲区一 | 低：只需在 pin-plan 加一个可选字段，检查它是否出现在图里 |
| 从 BOM 的器件属性读 `outputType`，检查开集输出的负载方向 | 盲区三 | 高：需要库里补数据 |
| 记录板级供电方式（USB/电池/外部），与电源网对照 | 盲区二 | 中：需要新的输入 |

**第一项最值得做**：它把"我认为这块板用哪个网络供电"变成可验证的声明，
而不是靠引脚名猜。

## 现在该怎么用

- 看到 `power_net: pass` → 说明**有电源类引脚，且它们都在同一个非地网络上**；
- 看到 `power_net: n/a` → **不代表没问题**，只代表"这一项没查到电源引脚"，
  需要人工确认这块板的电源是怎么接的。

`n/a` 不是通过，它是不适用——而"不适用"在这里可能意味着"我没认出来"。

## 盲区一已实测

构造一块「电源接在 GND 上、但符号用通用引脚名」的板：

```
status: n/a
reason: 图里没有电源类引脚（纯无源或未标注），这一项不适用
```

**和一块真正没有电源引脚的纯无源板，输出完全一样。**

这意味着：看到 `n/a` 时无法区分「确实没有电源引脚」和「有电源脚但名字不规范」。
两个场景的风险完全不同，却共用同一个结论——这正是需要 `power_nets` 显式声明的理由。

# 附：`erc` 那一项当时为什么没抓到（已查清）

第 98 轮那块板的电源脚全接在 GND 上，`erc` 判通过。我一直把这条当成技术债，
本轮查清了。

## metrics 里的描述

原来写的是：

```
'role': '电气规则：输出冲突/多驱动/无驱动/电源对地'
```

**「电源对地」这四个字读起来像"检查铜箔短路"，但它不是。**

## 实现实际做的事

`netlist_check.py`：

```python
power = set(data.get('power_nets', []))
ground = set(data.get('ground_nets', []))
for net in sorted(power & ground):
    add('阻断', 'net_class_conflict', net,
        '被同时声明为电源和地；这是输入分类冲突，不代表已测出铜短路')
```

它比较的是**输入里的两个声明列表**：有没有哪个网络名同时被列进 power_nets 和
ground_nets。它**不读引脚**，因此无法知道"某个电源脚接在 GND 上"。

代码自己的提示语已经写明了「不代表已测出铜短路」——**不诚实的只有 metrics 里那句
role 描述**，实现是对的。

## 两种情况必须分清

| 情况 | 定义 | 谁能抓 |
|---|---|---|
| 电源网与地网被重复声明 | 同一个名字同时出现在两个清单里 | `erc`（本次修正的是它的描述） |
| 电源**引脚**接在地**网络**上 | 图里 VCC 脚的网络名是 GND | **KPI 16**（先按引脚名，后改为声明式 `power_nets`） |

我们遇到的是第二种。

## 改了什么

`metrics/schematic-kpi.v1.json` 与技能副本里的 role 改为：

> 电气规则：输出冲突/多驱动/无驱动；以及电源网与地网被重复声明（输入分类冲突，不等于铜短路）

**不夸张一项检查的能力**，比多写几个字更重要——上一版描述会让人以为铜短路被查过了。

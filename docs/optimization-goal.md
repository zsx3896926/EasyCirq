# 优化方向盘点与目标定义

> 写于 2026-11-04，基于本会话已实测的数据。**未开跑，只有目标。**
> 所有数字都附来源；没量过的标 NOT RUN。

---

## 一、盘一遍：能优化的有六个方向

| # | 方向 | 现状（实测） | 不做的代价 | 收益确定性 |
|---|---|---|---|---|
| **A** | **规模天花板** | 最"大"的板是 **636×478×4 = 1.22M 节点 / 42 器件 / 566 线**。缓冲按 `L·W·H` 稠密分配，**这块板占 38.9 MB**（加 cost 两个缓冲 58.4 MB）。按板面积与层数外推见下表 | 面对 FPGA / AI 加速卡客户**内存先死**，不是慢 | **高**（代码里能指出哪一行会死） |
| **B** | **剩余 34% 时间** | `path_conflicts` 在 cProfile 里 **12.5 s**；A* 已从 65.9% 降到约 32% | 24.5 s/次，批量扫参数时是小时级 | 中（未 profile 过它自己的热点） |
| **C** | **单文件 3965 行** | `ec_layout.py` 一个文件装了板模型 / 布线器 / KPI / 检查 / 制造 | 改一处要读全文；新人上手慢 | 中（纯重构，有等价门禁保护） |
| **D** | **Python 依赖** | `minPython 3.10`，不打包 | 客户装完发现核心功能不可用 | 高（已判定为交付第一阻断） |
| **E** | **历史工程 → 规则管道** | 零。库靠人写 JSON | D5/D6 软肋：**多数企业有历史，没成文规范** | 高（但这是新能力，不是优化） |
| **F** | **IPC-2581 + CAM 验证** | Gerber 语法有效、回读通过、**未过 CAM** | 客户拿不出可交付的制造包 | 中 |

## 二、我的排序与理由

**选 A 和 B 合起来做，因为它们是一件事：让这套东西在客户真实规模上站得住。**

理由三条：

1. **A 是硬墙，不是慢。** 我看了代码：`_ensure(n)` 按 `L·W·H` 分配 4 个数组
   （`best` / `best_gen` / `came` / `came_gen`，各 8 字节），这块 636×478×4 的板
   是 **38.9 MB 常驻**（有 cost 时再加 19.5 MB）。

   **按板面积与层数外推（同样 5 mil 栅格）：**

   | 场景 | 栅格 W×H×层 | 节点数 | 4 个缓冲 |
   |---|---|---|---|
   | 现有板 ~80×60 mm，4 层 | 629×472×4 | 1.19 M | **0.04 GB** |
   | 手机板 ~150×70 mm，8 层 | 1181×551×8 | 5.21 M | 0.17 GB |
   | FPGA ~200×150 mm，12 层 | 1574×1181×12 | 22.3 M | **0.71 GB** |
   | AI 加速卡 ~400×500 mm，16 层 | 3149×3937×16 | 198 M | **6.35 GB** |
   | 细栅格 ~200×150 mm @2.5 mil，12 层 | 3149×2362×12 | 89.3 M | **2.86 GB** |

   **这不是"再优化一下"，是"换策略"。** 而且注意最后一行：**BGA 要细栅格，
   细栅格四倍放大节点**——高密度 BGA 和规模压力是同一个问题的两面。

   更正一处我先前写错的估算：我曾写"面积放大 10× ⇒ 4.8 GB"，那是把"面积 10×"
   和"每维 10×"混了。面积 10× 是 4 倍节点、约 0.16 GB。真正危险的是
   **每维数倍 + 层数翻倍 + 细栅格叠加**，见上表。

2. **客户问的第一个问题一定是规模。** 竞品宣传的是手机板、FPGA、AI 加速卡。
   我们现在拿不出 500 器件以上的任何一块板的数据。

3. **A 和 B 互相喂料。** 换成分级缓冲之后，A* 的常数项会变，**必须重测 B**；
   而 B 的重测又正好量出 A 的新策略对不对。

**D（Python 依赖）不放进这个目标**：它是打包问题，不是优化，而且和 A/B 无耦合。
**E（历史工程管道）不放进**：那是新能力，值得单独立目标，别和性能混在一起。

## 三、目标（一条）

> **让离线布局布线在"客户真实规模"上不再有隐形天花板：把规模曲线的拐点测出来、
> 把已知的密度缓冲墙换成分级策略、把剩余的热点按同一套门禁继续压下去，
> 并把「我们在多大就撑不住」写成客户能看懂的一句话。**

### 终态（四条，每条可验）

1. **有一条规模曲线**：至少 4 个规模档位（现有板 / 2× / 5× / 10× 面积的合成板，
   或真实大板），每档给出**网数 / 栅格节点 / 峰值内存 / 单次 route 时间**。
2. **已知的密度墙被拆掉**：`L·W·H` 的稠密分配不再是无条件路径。
   大图走稀疏/分块策略，**小板结果逐字节不变**。
3. **规模失效点被写下来**：超过哪个规模、以什么方式失败（内存 / 时间 / 精度），
   写进文档，**客户能看懂**，不是"性能有待优化"。
4. **剩余热点有结论**：`path_conflicts` 及其它 top-N 热点，要么优化并过门禁，
   要么量出上限后**明确不做**并记录。

### 判据（顺序不能颠倒）

1. **等价性先行**：动任何内核之前，`equivalence.py --write` 记录 plan SHA256。
   之后每次改动 `--compare` 必须 **逐字节相同**。现有基线（完整值，改一个字符都算放宽门禁）：

   · `retrocam/frontier-i`
     `27a311f6f7f3332eeacc7f15569686c327d11e0d6a7d50d48d81ccc9f5963ee9`
   · `selftest`
     `d0c7ef5bdac4863c8e05f88d58c635b498ea5d713e4351665960f1a494994732`
2. **KPI 指纹同时成立**：`bench.py --compare` 必须 `identical KPI fingerprint`。
3. **不许用"更快"换"不一样"**：本轮已经有过一次「快 4.1× 但 plan 从 555 线变 187 线」，
   是门禁拦下的 —— 那种改动不许进。
4. **规模数据必须真跑**：合成板要能说清怎么合成的；真实板要给出处。
   **没跑过的档位写 NOT RUN，不许外推。**
5. **不得放宽现有门禁**：`verify` 14 项、布局单测 124 条、全量 pytest 5093 条
   （当前基线）一条不许降。
6. **失败要说清楚**：内存不够就报内存不够，超时就报超时，**不许把"跑不动"说成"效果一般"**。

## 四、分阶段

### 阶段 1 · 先量，不改（这一步不许优化）

- [ ] 写 `scale_bench.py`：接受一组板子，输出 `网数 / 节点数 / 峰值内存 / 耗时`
- [ ] 用现有板 + 2× / 5× / 10× 合成板跑一遍，**找出实际崩在哪一档**
- [ ] 记录失败形态（MemoryError？交换抖动？还是单纯慢）
- [ ] 把曲线写进文档

**产出**：一条真实的规模曲线 + 一句"我们在 X 就撑不住"。
**验收**：曲线上的每个点都能用一条命令复现。

### 阶段 1 · 结果（已完成，见 [规模曲线](scale-curve.md)）

实测把原来的判断**推翻了一半**：

- **内存墙有明确阈值**：55M 节点时才 7.0 GB，约 127 字节/节点。阈值可在 50M 节点以上。
- **时间墙没有阈值而且更早**：网络 ×4 时耗时 ×23。这才是客户先遇到的。
- **面积放大反而更好布**：间距违规 237 → 41。所以「大板难」不成立，「密板难」成立。

x16 档位**未跑**（外推 28 GB vs 可用 16.9 GB，跑它会拖垮整机）。

### 阶段 2 · 拆墙（排序已按阶段 1 结果修正）

> 原计划是「先拆内存墙」。阶段 1 表明**内存不急、时间更急**，所以顺序改为：
> **先搞清时间随网络数超线性的原因，再决定要不要动缓冲。**


- [ ] 分级缓冲：节点数超过阈值时改走稀疏结构
- [ ] 阈值由阶段 1 的曲线决定，**不是拍脑袋**
- [ ] 每改一版跑 `equivalence --compare` + `bench --compare`
- [ ] 小板曲线不许退化（这是回归，不是优化）

**验收**：10× 档位的峰值内存显著下降，且小板 plan 逐字节不变。

### 阶段 3 · 剩余热点

- [ ] profile `path_conflicts`（cProfile tottime 12.5 s）
- [ ] 能优化的优化，过同一套门禁
- [ ] 不能优化的量出上限并写进"Measured and NOT kept"

**验收**：每个热点要么有改动 + 门禁通过，要么有上限数字 + 明确的"不做"。

### 阶段 4 · 收尾

- [ ] 文档：规模曲线、失效点、换来的与没换来的
- [ ] 技能参考补一句"这个规模以上别用"
- [ ] 全量回归 + 发版

## 五、这个目标明确不做

| 不做 | 为什么 |
|---|---|
| 不追竞品的模型/训练服务 | 那是新能力，且我们连客户成文规范都没拿到，没有数据 |
| 不做 Python 打包 | 是打包问题，和规模/性能无耦合，单独立目标 |
| 不动 A* 的搜索语义 | 只换数据结构与缓冲策略；换算法（跳点/双向）是另一个量级的风险 |
| 不为了规模降精度 | 粗栅格已经量过会让排序选错赢家（§185），不许拿它换速度 |
| 不碰"能不能交付"的结论 | RetroCam-02 做不到是物理决定的，任何优化都不改变这一点 |

## 六、为什么这个目标值得先做

**因为它是唯一一个"客户一问就露底"的方向。**

我们现在能证明的东西很硬：等价性门禁、人审不可绕过、19 项判据、离线全链路。
但客户第一个问题不会问这些，会问：

> **"我那块 2000 网的板，你这个跑得动吗？"**

现在这个问题**没有答案**，而且我知道答案很可能是"跑不动"，因为代码里那行
`_ensure(L*W*H)` 摆在那。

**把这句话从"不知道"变成"在 X 以内跑得动，超过 X 会这样失败"，本身就是交付物。**

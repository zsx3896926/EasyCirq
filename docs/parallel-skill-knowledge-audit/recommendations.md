# 按风险排序的建议（proposal only，不修改源 Skill）

依据：固定基线 `9a951ed` 的现场扫描、12 条已审规则、10 对已审关系、20 个阅读场景。
每条建议都给出可定位原文、触发场景、对速度/一致性的影响、建议改动、是否改变工程保护、
以及验证场景。**这些是提案，不是事实修复**；是否采纳由主维护者决定。

优先级：P1 = 高价值/低风险；P2 = 中；P3 = 清理项。完整机器清单见
`rule-review.md` 与 `benchmarks/skill-knowledge-audit/results/rules.json`。

## R1. 统一“等待/审批”的触发条件（P1）

- **触发场景**：用户说“直接改/一直做到 DRC”，Agent 仍在布局/交付点等待确认；或用户只要一次
  评审，Agent 把四个检查点都变成审批点。
- **原文位置**：`SKILL.md:96`（默认继续，仅用户明确说“先评审/这步给我看/确认后再布线”时等待）、
  `SKILL.md:226`（门禁是证据门不是审批门）、`design-gates.md:7`、`interaction.md:30`
  （只有用户要求分阶段确认或真正需要新决定时才等待）。
- **为何影响速度/一致性**：四处都合理，但触发词不完全一致（“检查点等待” vs “新决定”），
  Agent 容易按更保守的一处执行，产生额外等待。
- **建议变化（提案）**：保留默认“已授权范围继续”；在四处统一一句：
  “等待必须能回指用户明确原话，或改变已确认接口/尺寸/成本/范围的新决定；其余一律继续。”
- **是否改变工程保护**：否，收紧而非放松；证据缺失仍 BLOCKED。
- **验证场景**：`dev-12`（自主整板，不得出现 `wait_user_approval`）、`dev-13`
  （用户要求 `before_route`，必须出现等待）、`holdout-02`（范围扩张但用户禁止逐阶段确认）。

## R2. 合并“门禁不是审批门”的 5 处重复（P1）

- **触发场景**：新会话开工读 `SKILL.md` + `design-gates.md` + `interaction.md` 时，同一规则出现
  5 次，增加阅读轮次和误读概率。
- **原文位置**：`SKILL.md:96`、`:226`、`design-gates.md:7`、`:395`、`interaction.md:30`。
- **为何影响速度/一致性**：同义规则多处维护，版本变化时容易只改一处；用户看到“反复强调”
  会以为存在更严格的隐藏审批要求。
- **建议变化（提案）**：以 `design-gates.md:7` 为唯一正文；其余改为一句“见阶段门禁 §1”，
  保留 `SKILL.md` 的检查点节奏作为摘要（不重复完整条款）。
- **是否改变工程保护**：否，条款内容不变。
- **验证场景**：D1 重复主题数下降；`rules` 的 REL-01/REL-08 仍分类为
  `different_stage`/`ambiguity` 而非冲突；场景 must_include 不变。

## R3. 定义“做个板子”是否等于“明确要定制板”（P2）

- **触发场景**：新手说“做个板子”，同时现成模块能更快验证；Agent 可能在“画定制 PCB”和
  “推荐模块”之间摇摆。
- **原文位置**：`SKILL.md:42`（“做个板子”默认推进原理图及 PCB 候选）、
  `SKILL.md:84`（自定义 PCB 非必经；用户明确要定制板时保留）。
- **为何影响速度/一致性**：两条都读得通，但“明确要定制板”没有判别标准；plan 无法据文本确定
  范围，只能标 ambiguity（REL-06）。
- **建议变化（提案）**：在 L84 增补定义：仅当用户拒绝模块路线、或明说“定制/画板/不要模块”时，
  才视为“明确要定制板”；否则先给模块与定制两种路线的取舍。
- **是否改变工程保护**：否，只澄清路线默认。
- **验证场景**：新增两个 intent（现成模块 vs 明确定制），检查 required 中是否出现
  `schematic-authoring`/`pcb` 主题，以及 `unknown` 是否从 `ambiguity` 变为确定范围。

## R4. 区分“检查点等待”与“新决定处理”（P2）

- **触发场景**：布局前发现尺寸必须变化，同时用户要求“先评审”；Agent 不清楚应走检查点等待
  还是只登记新决定。
- **原文位置**：`design-gates.md:7`（四个可见检查点等待）、`interaction.md:30`
  （“真正需要新决定时才等待”）、`SKILL.md:96`（先处理该决定，同时推进无依赖部分）。
- **为何影响速度/一致性**：两处文本对“新决定是否属于检查点等待”未说明；当前只能标
  `ambiguity`（REL-08），不同 Agent 会做出不同等待行为。
- **建议变化（提案）**：明确“新决定 = 改变已确认接口/尺寸/成本/任务范围”，其处置是
  `decisions_required` 而不是通用 `wait_user_approval`；只有用户明确说“确认后再继续”才停。
- **是否改变工程保护**：否。
- **验证场景**：`dev-15`（scope_change 只产生 decisions，不自动等待）、`holdout-02`
  （scope/mechanical change + 禁止逐阶段等待）；检查 plan 的 `approval_gates` 与 actions。

## R5. 保持启动更新/环境检查为可选，纯分析跳过（P2）

- **触发场景**：用户只要一次资料分析或 BOM 核对，Agent 开工先跑更新检查/EDA 探测，首轮变慢。
- **原文位置**：`SKILL.md:15`（开始前“可用”`skill_update.py check`）、`:104`（纯分析无需提前
  连接/安装/探测 EDA）、`:110`（先跑 `doctor_env.py --summary` 的条件）。
- **为何影响速度/一致性**：“可用”是 may，但出现在开工段，容易被读成必做；与 L104 形成表面
  冲突（REL-02，实际 different_scope）。
- **建议变化（提案）**：在 L15 后加“纯分析任务跳过；只在准备实际读写工程或用户要求更新时运行”，
  并把 L104 的“无需”与 L110 的条件并列。
- **是否改变工程保护**：否；不连接 EDA 时仍如实标 NOT RUN。
- **验证场景**：`dev-10`/`holdout-01` 的 plan 不得含 `install`/`network`/`read_eda`；
  `holdout-03`（更新后继续）仍要求设计文档。

## R6. 合并“直连 vs 标签”的 5+ 处表述（P2）

- **触发场景**：画原理图时读到“局部直连/跨区用标签”“标签不乱飞”“不用全部打标签”等
  5+ 处近似句，误以为存在互斥规则。
- **原文位置**：`schematic-layout.md:13`、`:54`、`:74`、`workflow.md:31`、`SKILL.md:120`。
- **为何影响速度/一致性**：它们是同一条“默认+例外”的不同措辞；重复增加阅读，也给了
  “标签 vs 直连”被误读成冲突的空间（夹具 FX-02/04/11）。
- **建议变化（提案）**：以 `schematic-layout.md:74` + `:54` 为唯一“默认+例外”正文，其余改链接；
  保留 `SKILL.md:120` 的一句摘要。
- **是否改变工程保护**：否。
- **验证场景**：D1 重复主题数；`rules` 中 REL-03/REL-04 分类稳定；原理图场景 required 不变。

## R7. 明确 BLOCKED 只影响依赖链路（P2）

- **触发场景**：Connector 不可用或缺 Gerber 时，Agent 把整个任务停住，连可做的离线分析也不做；
  或反向把“离线继续”误读成可以写通过。
- **原文位置**：`design-gates.md:63`（缺证据就是 BLOCKED，不是 PASS）、
  `SKILL.md:112`（缺少执行通道仍可完成方案/计算/离线规划，但不得说成已完成）。
- **为何影响速度/一致性**：两条方向一致，但“BLOCKED”的作用范围未写清；用户会感到“检查严格”
  与“继续推进”矛盾（REL-05，实际 coexist）。
- **建议变化（提案）**：在 `design-gates.md:63` 后加一句：“BLOCKED 只影响依赖该证据的链路；
  不依赖它的离线分析继续，但相关结论保持 NOT RUN。”
- **是否改变工程保护**：否；反而减少“假通过”和“过度停顿”两种误读。
- **验证场景**：`dev-10`（离线继续 + `eda_unavailable`）、`holdout-05`（缺证据停依赖链）；
  检查 plan 不产生 `write_eda`，但保留 `offline_analysis`。

## R8. 修正 15 个“括号前截断”锚点或声明约定（P2）

- **触发场景**：点击/生成 `common-hardware/README.md` 里的 `#g1-ldo`、`#g5-反相电源` 等锚点，
  在 GitHub 精确 slug 下找不到；只在“截断到括号前”的约定下可解析。
- **原文位置**：`references/common-hardware/README.md:29,35`、`applications/02:33`、
  `03:27,40`、`05:29`、`07:114,160`、`11:99`、`12:108` 等 15 处；
  另有 `03:27` 的 `I²C` vs `I2C` 兼容折叠差异 1 处。
- **为何影响速度/一致性**：不影响 AI 阅读正文，但影响“引用是否有效”的可点击质量与维护信任；
  工具只能给 `anchor_prefix_match` 警告而不能判失效。
- **建议变化（提案）**：统一改为完整 GitHub slug（如 `#g1-ldo低压差线性稳压`），或在
  `common-hardware/README.md` 声明“锚点只取括号前段”的渲染约定并让工具识别为已声明约定。
- **是否改变工程保护**：否。
- **验证场景**：`scan` 的 `anchor_prefix_match` 从 15 降到 0（或全部落入显式忽略声明）；
  `anchor_compat_match` 处理 `I²C` 一处。

## R9. 安装示例版本号改为占位符（P3）

- **触发场景**：用户照安装文档复制 `design-hardware-0.8.0.zip` 命令，误以为当前版本是 0.8.0。
- **原文位置**：`references/installation-updates.md:65-67`（`0.8.0` 出现在 3 条命令）、
  `:81`（`v0.8.0` 示例）；当前 `.version` 为 `1.0.1`。
- **为何影响速度/一致性**：示例版本与当前版本不一致，会造成无效命令和版本误判；属于示例
  陈旧，不是规则错误。
- **建议变化（提案）**：用 `<version>` 占位并注明“示例版本”，或改为 `1.0.1` 并加维护检查。
- **是否改变工程保护**：否。
- **验证场景**：文档 lint/规则夹具 FX-10 类“代码示例”不被当规则；安装示例路径存在性检查。

## R10. 门禁字段枚举用完整字段名（P3）

- **触发场景**：维护者核对不可豁免字段时，`design-gates.md:80` 的“前六个字段”与 L76 的
  `req_` 前缀字段列表需要人工映射，容易配错豁免。
- **原文位置**：`design-gates.md:76`（12 个 `req_*` 字段）、`:80`（“前六个字段”只写
  `delivery_level` 等短名）。
- **为何影响速度/一致性**：同一集合两种命名，增加阅读与配置错误风险；不影响不可豁免集合本身。
- **建议变化（提案）**：L80 直接重复 L76 的六个完整字段名（`req_delivery_level` 等），
  不改变可豁免/不可豁免集合。
- **是否改变工程保护**：否（集合不变）。
- **验证场景**：构造缺 `req_environment_accuracy` 的 design-state 仍判 BLOCKED；
  `gate_check.py` 现有用例不变。

## 不建议做的事

- 不把所有长文档判为坏文档：`source-register.md`、`common-hardware/*`、`design-gates.md`
  体量大但大多按需读取；真正的问题是入口重复与边界歧义。
- 不为“更快”弱化身份保护、证据真实性、G2/G3 前置或保存重开验收。
- 不用字符串相似度直接删规则；本报告只给 proposal，采纳前需维护者复核条件与例外。

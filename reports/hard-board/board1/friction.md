## #1 `sch list --json` 不接受 `--json`

| | |
|---|---|
| **分类** | 产品缺陷（一致性） |
| **发现方式** | 落器件后想读回，按惯例加了 `--json` |

| **分类** | 产品缺口（批量写入缺少"放置并核实"的封装） |
| **发现方式** | 批量落 49 个器件，报"落下 22、失败 27"，但读回是 **50 个** |

## #4 daemon 因版本升级重启 → 连接器掉线 → 门立刻报 BLOCKED

| | |
|---|---|
| **分类** | 产品缺陷（体验：升级后的第一条命令必然失败一次） |
| **发现方式** | 重建 CLI 到 1.4.2 / 1.4.3 后，**每条**要碰 daemon 的命令都触发一次自动重启 |
| **原始输出** | `daemon 1.4.2 落后于 CLI 1.4.3，正在后台重启…` → `sch gate: BLOCKED — no connected window` |
| **影响** | 升级后第一次跑门必失败。文案已说明"不是板子的问题"，但用户仍要自己等 ~8–10 秒。**每次升级都会撞一次。** |
| **修法** | 门遇到「no connected window」这类**掉线原因**时，自己等连接器回来并重跑（最多 15 秒，每秒一次）。等不到**仍然如实报 BLOCKED**，绝不改成通过或失败。只认这一类原因——别的 BLOCKED 立刻返回，不为不相干的故障白等。 |
| **验证** | 真机：把 CLI 升到 1.4.4（daemon 尚在 1.4.3）后**立刻**跑门。旧行为是 `BLOCKED`，现在等 **12.6 秒**后拿到 **`sch gate: PASS`**。单测 4 条（Recovers / GivesUpHonestly / Unrelated 不等待 / 原因识别）。 |
| **提交** | ✅ 1.4.4 |

## #7 用 `sch connect` 批量连线会物理短路；该用 `sch autoconnect`

| | |
|---|---|
| **分类** | 文档缺失（工具没选对）+ 产品可改进（`connect` 不提示碰撞）|
| **发现方式** | 连完 115 个引脚后读回，`+5V` 一个网络有 **37 个引脚**（我只挂了 9 个）——不同网络被合并了 |
| **门的判定** | `bridge-check: 6 wire-bridge(真短路)` + `clusters: 37 处组间图元重叠` |
| **根因** | 器件按 110×90 网格摆放，`sch connect` 用它自己的默认偏移放引线与网络标号，**相邻引脚的标号在物理上重叠**，于是电气上并成一个网 |
| **正确工具** | `sch autoconnect` —— 按真实几何（器件 bbox、引脚坐标、已有标号 bbox、标题栏禁区）给每个「方向 × 偏移」候选打分，取最低代价；幂等（已在目标网上的引脚跳过）；`--spec` 批量；`--strict` 拒绝有碰撞的候选 |
| **修法** | 板1 的连线要**用 `autoconnect --spec` 重做**，并对已连错的先用 `--replace` 清理 |
| **值得记的一条** | **门抓住了它**：`bridge-check` 报 6 处真短路。脚本可以糊弄，门不行。 |
| **提交** | 记录 + 板1 的连线下一轮重做 |

## #10 `--replace` 在降级连接器上会**震荡**

| | |
|---|---|
| **分类** | 产品缺陷（破坏性操作 + 假失败 = 自我打架） |
| **发现方式** | 分块重跑 6 轮，已连引脚数在 76 → 100 → 76 → 98 → 76 → 83 → 91 之间来回跳，网络数一直卡在 37 |
| **根因** | `--replace` 是"删旧标号 + 重连"。在连接器降级时，**删除可能落上而重连没落上**（或反之），于是每一轮都在拆上一轮的成果 |
| **影响** | **修复动作本身在破坏**。越重跑越不确定。 |
| **正确姿势（本轮学到）** | 降级状态下**不要反复 `--replace`**。要么先一次性清干净再从零连（不带 `--replace`），要么停下等连接器恢复 |
| **修法** | `--replace` 在开跑前先探一次连接器（一次只读 `components.list`，看它的 warnings），降级就**直接拒绝**并说明会发生什么 |
| **验证** | 单测 `TestThrottleRefusesReplaceWhenDegraded` / `TestThrottleAllowsReplaceWhenHealthy`；真机：连接器健康时 `--replace --dry-run` 放行（ok:true）|
| **提交** | ✅ 1.4.6 |

## #13 批量改布局**没有事务**：半途失败会停在中间态

| | |
|---|---|
| **分类** | 产品缺陷（批量操作的原子性） |
| **发现方式** | 重排 51 个器件时连接器降级，只有 **25 个**移动成功，其余没动 |
| **证据** | `已重排: 25 / 51  最大 x=370`（第一轮完整重排时是 `51/51 最大 x=1095`）|

## #31 `sch modify` 移器件**不移标号** → 孤立标号堆积 → 组间重叠

| | |
|---|---|
| **分类** | 产品缺口（与 #30 同族：**没有任何命令能把"器件 + 它的标号"当作一个整体移动**） |
| **现象** | `sch modify --x 300 --y 760` 把 R7 挪走，返回 `ok: true`。但 `clusters` 仍报 `1 处组间图元重叠 (R7 ↔ U3)` |

| **机理** | 单件移动只改器件坐标。挂在它引脚上的桩线/标号留在原处 → 变成孤立图元 → 计入该器件的"组" → 与邻居重叠 |
| **为什么之前没暴露** | `layout-lint` 只看器件本体，`check` 只看线/几何；**只有 `clusters`（按组算）会把孤立标号算进去**。三条判据各看一层，正好覆盖 |
| **这对用户意味着** | 挪一个器件之后，图面看起来正常、`layout-lint` 也 PASS，但 `clusters` 会永久红着，而**红的原因不在这个器件身上**（它在 300,760，重叠在 610,320）。排查成本很高 |
| **应当改** | ① `sch modify` 加一个 `--move-attachments`（或用 `--group` 语义）把桩线/标号一起挪；<br>② **或者** `clusters` 的重叠报告里指出"这是孤立标号造成的"，并给出 `sch disconnect --flag-id …` 的可执行命令；<br>③ 至少给一个 `sch gc`（清理孤立标号） |
| **当前处置** | **未修**。板1b 停在这 1 处重叠上。这是**我连续三次移动造成的残留**，不是产品自己产生的脏数据。 |

| 原路移回 | 连接 31→44，但产生 `wire-through-body (U3)` |

| **只有一处检查了它** | `sch_connectivity_merge.go:144` 是唯一读 `scope.settled` 的调用方；其余（`list` / `reconcile` / `check` …）全部忽略 |
| **修法** | `switchToPage` 在**真的切过页却没就绪**时**报错**，并说清"读到的器件数不可信，不要当成空页"；要宽松语义的调用方显式用 `switchToPageBestEffort` |
| **为什么不一律报错** | 本来就在这一页、探针也没稳定，说明这一页此刻就是这样，读它不比别的时候更不可信。只在**切页**场景报错才既准又不误伤 |
| **测试** | `TestSettleGateErrorsOnlyWhenItActuallySwitched`：切页+未就绪→报错（且点名"不可信""不要当成空页"）；就绪→不报；**没切页→不报** |

### 真机验证（这次修复自己证明了它）

修之前，同一批命令读 P3 报 **0 个器件**，我据此"复核已空"。
修之后，同一条 `sch list --page P3` 报 **24 个器件** ——


### 顺带确认的第二件事

带上 `--doc <page>` 才真的删掉 24 个。

> **读要页面对（由 settle 闸门保证），写要 `--doc` 钉住。两件事都不能省。**

## 2026-11-05 批量测量落地：38/39 型号量出引脚几何

`easycirq/scripts/sch_measure_parts.py`，链路全部**只读**：

```
part id → standard-parts 的 C 号
  → lib by-lcsc      (libraryUuid + deviceUuid)
  → lib device get   (symbolUuid)
  → lib symbol export-source   (.elibz2)
  → 解析 ProLib_*.elibu        (引脚名/坐标/旋转/长度/接触点)
```

### 结果

```
型号 39 个：命中缓存 2，新取 36，失败 1
量出引脚几何：38 个型号，合计 110 个引脚
零引脚型号：无
```

抽样（`ic.xl1509_5v_buck`）：

```
FB      x=-55 y=10  rot=0    cp=(-35, 10)
GND     x=55  y=30  rot=180  cp=(35, 30)
GND#2   x=55  y=10  rot=180  cp=(35, 10)
GND#3   x=55  y=-10 rot=180  cp=(35,-10)
GND#4   x=55  y=-30 rot=180  cp=(35,-30)
```

**同名引脚做了编号区分**（`GND#1..#4`）——否则 4 个地脚的几何会互相覆盖，
与网表 join 时错位。

### 缓存

导出件落在 `.easycirq/symbol-cache/`，命中就不重复请求（实测第二次跑命中 2 个）。
不缓存的话每次都要几十次往返。

### 四条测试

- 绝大多数型号有引脚几何，且每个引脚都有坐标
- **同名引脚能分开**（4 个地脚接触点互不相同）
- **失败留在 `problems` 里**，不静默跳过
- 量出来的型号必须都在网表里（量了用不上的说明链子接错）

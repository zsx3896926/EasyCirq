## #1 `sch list --json` 不接受 `--json`

| | |
|---|---|
| **分类** | 产品缺陷（一致性） |
| **发现方式** | 落器件后想读回，按惯例加了 `--json` |
| **命令** | `easycirq sch list --project <uuid> --json` |
| **原始输出** | `unknown flag: --json` |
| **影响** | `phase` / `card` / `status` / `sch status` 都支持 `--json`，唯独 `sch list` 不支持——而它**本来就输出 JSON**。任何按惯例写脚本的人（或 Agent）都会直接失败。 |
| **修法** | 把 `--json` 加成**接受但无副作用**的兼容开关，帮助里说明原因。惯例应当可依赖，"记住哪几条命令例外"永远会有人忘。 |
| **验证** | 修后 `sch list --json` 返回 `ok:true count:2` |
| **提交** | ✅ 1.4.2 |

## #2 `sch place` 报失败，但器件其实落上了（27/49）

| | |
|---|---|
| **分类** | 产品缺口（批量写入缺少"放置并核实"的封装） |
| **发现方式** | 批量落 49 个器件，报"落下 22、失败 27"，但读回是 **50 个** |
| **证据** | 页面位号 `C2 C3 C5 CAD1 CAD2 CB1 CD2 CSEQ1 CSEQ2 D2 D3 D4 Q_REV RAD1 RAD2 RAD4 RCC1 RCC2 RFB1 RFB2 RFB3 RFB4 RL2 RL3 RRST RSEQ2 U4` —— 这 27 个全在板上，**无重复、无空位号** |
| **产品自己怎么说** | `warnings` 里写着：<br>`connector looks DEGRADED under load (recent failure rate 45%) — this write may have LANDED despite the failure (假失败定律): verify with a light read before resending, and do NOT blind-retry.`<br>`degraded: {recentFailureRate: 0.45, verifiedSamples: 0}` |
| **影响** | 在连接器高负载下，`ok:false` **不等于没写成功**。信退出码的自动化流程要么重试造重复器件，要么中止以为没落下。**批量写入必踩。** |
| **我的用法也有问题** | 我的脚本只看了 `ok`，没读 `warnings`。这条同时是"产品该封装"和"调用方该读警告"。 |
| **修法（待做）** | 给 `sch place` 加 `--verify`：失败时做一次轻量读回，明确报告 `landed: true/false`，让调用方不必自己记得去核实。`verifiedSamples: 0` 说明核实机制存在但没接上。 |
| **修法** | 给 `sch place` 加 `--verify`：失败时读回一次，明确回答 `landed: true/false`。判定逻辑抽成纯函数 `scanForPlacement`，6 条单测覆盖（含「图框不算器件」「读回空了不能算成功」）。 |
| **验证** | 真机实测：故意用错的 device uuid → 报失败后读回 `读回核实：没落上（读回里没有位号 RX2）。可以安全重试。` |
| **提交** | ✅ 1.4.3 |

## #4 daemon 因版本升级重启 → 连接器掉线 → 门立刻报 BLOCKED

| | |
|---|---|
| **分类** | 产品缺陷（体验：升级后的第一条命令必然失败一次） |
| **发现方式** | 重建 CLI 到 1.4.2 / 1.4.3 后，**每条**要碰 daemon 的命令都触发一次自动重启 |
| **原始输出** | `daemon 1.4.2 落后于 CLI 1.4.3，正在后台重启…` → `sch gate: BLOCKED — no connected window` |
| **影响** | 升级后第一次跑门必失败。文案已说明"不是板子的问题"，但用户仍要自己等 ~8–10 秒。**每次升级都会撞一次。** |
| **修法** | 门遇到「no connected window」这类**掉线原因**时，自己等连接器回来并重跑（最多 15 秒，每秒一次）。等不到**仍然如实报 BLOCKED**，绝不改成通过或失败。只认这一类原因——别的 BLOCKED 立刻返回，不为不相干的故障白等。 |
| **验证** | 真机：把 CLI 升到 1.4.4（daemon 尚在 1.4.3）后**立刻**跑门。旧行为是 `BLOCKED`，现在等 **12.6 秒**后拿到 **`sch gate: PASS`**。单测 4 条（Recovers / GivesUpHonestly / Unrelated 不等待 / 原因识别）。 |
| **提交** | ✅ 1.4.4 |

## #6 `lib search` 返回不相关器件，导致选错料（板1 上错了 3 个）

| | |
|---|---|
| **分类** | 产品缺陷（严重：静默选错料） |
| **发现方式** | 编网络表时核对引脚数才发现 |
| **证据** | 期望 TVS → 得到 `PCA9554DGVR`（8 位 I2C 扩展器，16 脚）<br>期望 AMS1117 LDO → 得到 `DO3314-333MLC` / `AGM613AP`<br>期望 1.8V LDO → 落到 150V N 沟道 MOSFET（U4，5 脚） |
| **影响** | **比"查不到"危险得多**：查不到会让人换关键词；查到错的会一路错到打样。板1 已这样放了 3 个器件。 |
| **根因** | 连接器是相关度排序，**没有真正匹配时也返回前 N 条**，CLI 原样透传 |
| **修法** | 默认加一道闸：查询词没出现在器件可读字段里的候选不返回；全被筛掉时明确说"没有匹配"。`--allow-fuzzy` 保留原行为。 |
| **修法里的两个坑**（都在同一次改动里踩到）| ① **词边界**：封装名 `TVSOP-48` 里含 `tvs`，裸 Contains 让每次 TVS 查询都命中 TVSOP 封装的任意器件<br>② **边界太紧**：`STM32F030` 是 `STM32F030C8T6` 的前缀，硬要词边界会把真正想要的型号筛掉<br>最终规则：**短词（≤3 字符）要词边界，长词（≥4 字符）直接包含** |
| **还有一条** | 只过滤前 N 条会误杀后面才出现的真匹配 → 改成**多取（20 条）再筛再截断** |
| **验证** | 真机：`STM32F030` 3 命中 0 筛；`TVS SMBJ` 0 命中 10 筛并明确报"没有匹配"；`10k 0603` / `100nF 0603` / `TPS54331` 均命中 |
| **单测** | 5 条（错配识别 / token 拆分 / 过滤 / 词边界 / 型号前缀）|
| **提交** | ✅ 1.4.5 |
| **仍待做** | 板1 上那 3 个错料要**删掉重放**（本轮的过滤器只能防止以后再选错，不能自动纠正已放下的）|

## #7 用 `sch connect` 批量连线会物理短路；该用 `sch autoconnect`

| | |
|---|---|
| **分类** | 文档缺失（工具没选对）+ 产品可改进（`connect` 不提示碰撞）|
| **发现方式** | 连完 115 个引脚后读回，`+5V` 一个网络有 **37 个引脚**（我只挂了 9 个）——不同网络被合并了 |
| **门的判定** | `bridge-check: 6 wire-bridge(真短路)` + `clusters: 37 处组间图元重叠` |
| **根因** | 器件按 110×90 网格摆放，`sch connect` 用它自己的默认偏移放引线与网络标号，**相邻引脚的标号在物理上重叠**，于是电气上并成一个网 |
| **正确工具** | `sch autoconnect` —— 按真实几何（器件 bbox、引脚坐标、已有标号 bbox、标题栏禁区）给每个「方向 × 偏移」候选打分，取最低代价；幂等（已在目标网上的引脚跳过）；`--spec` 批量；`--strict` 拒绝有碰撞的候选 |
| **修法** | 板1 的连线要**用 `autoconnect --spec` 重做**，并对已连错的先用 `--replace` 清理 |
| **值得记的一条** | **门抓住了它**：`bridge-check` 报 6 处真短路。脚本可以糊弄，门不行。 |
| **提交** | 记录 + 板1 的连线下一轮重做 |

## #8 难度门槛里"网络数 ≥80"对 51 个器件的板子偏高

| | |
|---|---|
| **分类** | 目标设定问题（我自己的门槛定高了） |
| **实测** | 51 器件 / 167 引脚，按功能块合理成网后是 **35 个网络**（含 GND、VBUS、四路电源轨、反馈、使能、采样、LED、MCU） |
| **为什么** | 网络数不是器件数的一半：大量引脚落在同一组电源/地上（GND 一个网就吃掉 30 个引脚）。真要到 80 个网络，得让每个 GPIO 都单独成网，那是为了凑数，不是为了功能。 |
| **处置** | **不改门槛**（目标文档写明"边跑边改目标"不做）。本轮据实记为**未达标**，并把实测值记下来；板2 门槛（≥120 网络 / ≥60 器件）届时同样实测再评。 |

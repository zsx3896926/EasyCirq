## #1 `sch list --json` 不接受 `--json`

| | |
|---|---|
| **分类** | 产品缺陷（一致性） |
| **发现方式** | 落器件后想读回，按惯例加了 `--json` |

| **分类** | 产品缺口（批量写入缺少"放置并核实"的封装） |
| **发现方式** | 批量落 49 个器件，报"落下 22、失败 27"，但读回是 **50 个** |

## #4 daemon 因版本升级重启 → 连接器掉线 → 门立刻报 BLOCKED

| | |
|---|---|
| **分类** | 产品缺陷（体验：升级后的第一条命令必然失败一次） |
| **发现方式** | 重建 CLI 到 1.4.2 / 1.4.3 后，**每条**要碰 daemon 的命令都触发一次自动重启 |
| **原始输出** | `daemon 1.4.2 落后于 CLI 1.4.3，正在后台重启…` → `sch gate: BLOCKED — no connected window` |
| **影响** | 升级后第一次跑门必失败。文案已说明"不是板子的问题"，但用户仍要自己等 ~8–10 秒。**每次升级都会撞一次。** |
| **修法** | 门遇到「no connected window」这类**掉线原因**时，自己等连接器回来并重跑（最多 15 秒，每秒一次）。等不到**仍然如实报 BLOCKED**，绝不改成通过或失败。只认这一类原因——别的 BLOCKED 立刻返回，不为不相干的故障白等。 |
| **验证** | 真机：把 CLI 升到 1.4.4（daemon 尚在 1.4.3）后**立刻**跑门。旧行为是 `BLOCKED`，现在等 **12.6 秒**后拿到 **`sch gate: PASS`**。单测 4 条（Recovers / GivesUpHonestly / Unrelated 不等待 / 原因识别）。 |
| **提交** | ✅ 1.4.4 |

## #7 用 `sch connect` 批量连线会物理短路；该用 `sch autoconnect`

| | |
|---|---|
| **分类** | 文档缺失（工具没选对）+ 产品可改进（`connect` 不提示碰撞）|
| **发现方式** | 连完 115 个引脚后读回，`+5V` 一个网络有 **37 个引脚**（我只挂了 9 个）——不同网络被合并了 |
| **门的判定** | `bridge-check: 6 wire-bridge(真短路)` + `clusters: 37 处组间图元重叠` |
| **根因** | 器件按 110×90 网格摆放，`sch connect` 用它自己的默认偏移放引线与网络标号，**相邻引脚的标号在物理上重叠**，于是电气上并成一个网 |
| **正确工具** | `sch autoconnect` —— 按真实几何（器件 bbox、引脚坐标、已有标号 bbox、标题栏禁区）给每个「方向 × 偏移」候选打分，取最低代价；幂等（已在目标网上的引脚跳过）；`--spec` 批量；`--strict` 拒绝有碰撞的候选 |
| **修法** | 板1 的连线要**用 `autoconnect --spec` 重做**，并对已连错的先用 `--replace` 清理 |
| **值得记的一条** | **门抓住了它**：`bridge-check` 报 6 处真短路。脚本可以糊弄，门不行。 |
| **提交** | 记录 + 板1 的连线下一轮重做 |

## #10 `--replace` 在降级连接器上会**震荡**

| | |
|---|---|
| **分类** | 产品缺陷（破坏性操作 + 假失败 = 自我打架） |
| **发现方式** | 分块重跑 6 轮，已连引脚数在 76 → 100 → 76 → 98 → 76 → 83 → 91 之间来回跳，网络数一直卡在 37 |
| **根因** | `--replace` 是"删旧标号 + 重连"。在连接器降级时，**删除可能落上而重连没落上**（或反之），于是每一轮都在拆上一轮的成果 |
| **影响** | **修复动作本身在破坏**。越重跑越不确定。 |
| **正确姿势（本轮学到）** | 降级状态下**不要反复 `--replace`**。要么先一次性清干净再从零连（不带 `--replace`），要么停下等连接器恢复 |
| **修法** | `--replace` 在开跑前先探一次连接器（一次只读 `components.list`，看它的 warnings），降级就**直接拒绝**并说明会发生什么 |
| **验证** | 单测 `TestThrottleRefusesReplaceWhenDegraded` / `TestThrottleAllowsReplaceWhenHealthy`；真机：连接器健康时 `--replace --dry-run` 放行（ok:true）|
| **提交** | ✅ 1.4.6 |

## #13 批量改布局**没有事务**：半途失败会停在中间态

| | |
|---|---|
| **分类** | 产品缺陷（批量操作的原子性） |
| **发现方式** | 重排 51 个器件时连接器降级，只有 **25 个**移动成功，其余没动 |
| **证据** | `已重排: 25 / 51  最大 x=370`（第一轮完整重排时是 `51/51 最大 x=1095`）|

## #31 `sch modify` 移器件**不移标号** → 孤立标号堆积 → 组间重叠

| | |
|---|---|
| **分类** | 产品缺口（与 #30 同族：**没有任何命令能把"器件 + 它的标号"当作一个整体移动**） |
| **现象** | `sch modify --x 300 --y 760` 把 R7 挪走，返回 `ok: true`。但 `clusters` 仍报 `1 处组间图元重叠 (R7 ↔ U3)` |

| **机理** | 单件移动只改器件坐标。挂在它引脚上的桩线/标号留在原处 → 变成孤立图元 → 计入该器件的"组" → 与邻居重叠 |
| **为什么之前没暴露** | `layout-lint` 只看器件本体，`check` 只看线/几何；**只有 `clusters`（按组算）会把孤立标号算进去**。三条判据各看一层，正好覆盖 |
| **这对用户意味着** | 挪一个器件之后，图面看起来正常、`layout-lint` 也 PASS，但 `clusters` 会永久红着，而**红的原因不在这个器件身上**（它在 300,760，重叠在 610,320）。排查成本很高 |
| **应当改** | ① `sch modify` 加一个 `--move-attachments`（或用 `--group` 语义）把桩线/标号一起挪；<br>② **或者** `clusters` 的重叠报告里指出"这是孤立标号造成的"，并给出 `sch disconnect --flag-id …` 的可执行命令；<br>③ 至少给一个 `sch gc`（清理孤立标号） |
| **当前处置** | **未修**。板1b 停在这 1 处重叠上。这是**我连续三次移动造成的残留**，不是产品自己产生的脏数据。 |

| 原路移回 | 连接 31→44，但产生 `wire-through-body (U3)` |

## #46 引脚几何三处错，**求解器全是对的**（已修）

求解器一直报 `pin-exit-blocked: <ref>.<pin> minimum outward segment crosses <ref> body`。
我一度怀疑是求解器的问题。**读实现并逐条验证后，三处错都在我的度量上**：

| # | 我做的 | 事实 | 后果 |
|---|---|---|---|
| 1 | `connection_point = x + cos(rot)*length` | `.elibu` 的 **`x,y` 本身就是引脚连接点**，`rotation` 是"朝本体"的方向 | 连接点被推进本体内部 |
| 2 | 把文件里的 `rotation` 直接交给求解器 | 求解器要的是**世界朝外角** = rotation + 180 | 所有引脚"朝内" |
| 3 | 本体框用"引脚范围 + padding" | 引脚是从本体**伸出来**的，落在框内就必然"朝外段穿过本体" | 一条位置都排不下 |
| — | 用"离引脚中心最远的主轴"推朝外 | EP（外露焊盘）在引脚范围中间，判反 | `X2.EP` 继续报错 |

**最终做法**：本体用符号自己的 `RECT`（TPS54360 是 x −40..40 / y −25..25），
引脚朝外 = 引脚在本体外侧的哪一边。**不发明本体，用符号给的。**

没有 `RECT` 的符号（电感、端子、二极管）用两遍法：先按 `rotation+180` 朝内退 `length`
推出本体，再用同一套规则算朝向；推出的本体**也要保证非退化**（两脚件引脚共线，
退完在某轴厚度为 0，`plBoxValid` 会拒）。

### 修完的实证

| | 修之前 | 修之后 |

## #53 的**根因**已修：未知输入不许静默回落

上一轮只补了前缀表 —— 那只是消除症状。真正的根因是：

```python
return PREFIX.get(head, "X")     # 未知前缀 → 静默产出 X
```

**`X` 看起来像正常结果**，于是它一路流到 BOM、丝印、KPI 判据，没人察觉。

### 三处根因，全部改成响亮失败

| 处 | 旧行为 | 新行为 |
|---|---|---|
| `ref_prefix()` | 未知前缀 → `"X"` | **抛 `UnknownPartPrefix`**，报文点名前缀 + 指出要改 `PREFIX` |
| 内网命名 | 未知角色 → 网名 `X_N3` | 记 **error issue** 并跳过该网（不产出无意义网名） |
| 管线 `has_ic` | 只看位号 `U*`/`IC*` | **先看器件身份**（型号前缀），位号只作兜底 |

第三条是更深的一层：**位号是派生数据，用派生数据判语义，生成规则一变就静默误判。**
#53 正是这样——`buck.*` 落成 `X2`，管线就以为"这页没有 IC"。

### 护栏测试：14 条，钉的是根因不是症状

| 组 | 断言 |
|---|---|
| 响亮失败 | 未知前缀**必须抛错**；报文点名前缀、指出改哪里 |
| 覆盖度 | **标准件表**与**块库**里的每一个前缀都有映射（新器件从这两个入口进来）|
| 禁止回落 | `PREFIX` 里**没有任何**前缀映射到 `X`（`X` 只能是显式选择）|
| IC 判定 | **位号写成 `X2` 的 buck 也必须被认成 IC**（8 组正反例）|

### 验证：正常路径不受影响

```
离线链：全部通过 ✅（S1–S6 七步全绿）
故意喂未知前缀：✅ 抛错 —— 型号 'zzz_unknown.whatever' 的前缀 'zzz_unknown'
              没有位号映射 —— 请在 PREFIX 里补上（IC 类一律 'U'），不要让它回落成 X
```

**响亮失败不会打断正常流程，只会在真出错时拦住你。**

### 这一类 bug 的通用教训

> **回落值只要"看起来像正常结果"，就会一路流下去。**
> 未知输入应当**响亮失败**，而不是产出一个可信度不明的默认值。

这条适用于所有映射表、判据、默认纸型 —— 后面再遇到同类，先问一句
"这里回落出来的东西，会不会看起来像正常工作？"

## #54 `pin_mux` 的适用性用粗代理判，把纯电源板也拖了进来

挡了五块的最后一件事是「没有引脚规划表」。查清后发现：**这块板根本不需要它。**

### 事实

`pin_plan_check.py` 判的是 **MCU 的引脚复用与资源分配**（`mcu.ref`、
`pins[].logical`、pinmux、资源预算）。而板2 用的是
`buck` / `buckboost` / `ic`（电源芯片）——**引脚是固定功能，没有复用可言**。

全板**没有任何 MCU**（型号前缀分布：conn/fuse/mos/res/zener/diode/cap/buck/ind/ic/buckboost）。

而管线用 `has_ic`（有任何 IC）当代理判据 → 纯电源板也被要求交引脚规划表。

### 这与 #53 是同一类错

> **用粗代理做适用性判断，代理和被测对象不是一回事。**

#53 是「位号前缀」代理「是不是 IC」；#54 是「是不是 IC」代理「有没有复用资源」。
两次都把不该判的东西判了，而且**方向都是"多判"** —— 把不适用记成缺失，门永远开不了。

### 修法与它为什么不是放宽

判据改成 `has_mcu`（MCU/SoC/FPGA 类前缀）：

```python
has_mcu = any(_is_mcu_component(c) for c in ir_data["components"])
if not has_mcu:
    # 写 pinplan 检查为 n/a，理由写明"没有复用资源"
```

**这不是放宽守卫**：只要板上有 MCU，没规划表照样 `missing` → 阻断。
判据门限一条没动，只是把"不适用"判对了。

### 验证

| 模块 | verdict | pin_mux | apply_allowed |
|---|---|---|---|
| M1–M5 | **PASS** | `na` | **True** |

连跑两轮满足稳定性要求（连续 2 轮 PASS）。

### 护栏测试（14 条）

| 组 | 断言 |
|---|---|
| MCU 判定 | `mcu/stm32/fpga/soc` → 是；`buck/buckboost/ldo/ic(电源)` → **不是** |
| 板2 事实 | 型号前缀与 MCU 集合**无交集** |
| **守卫没放宽** | 有 MCU 又没规划表 → `pin_mux` **必须 missing** 并进 blockers、判词 BLOCKED（在 **KPI 层**验证，与管线写不写 na 无关）|
| 源码层 | na 分支条件必须是 `has_mcu`，不许再出现 `has_ic` |
| 说明可读 | `na` 的 note 要点出"没有 MCU/SoC"与"固定功能" |

### 判据小结：三次"多判"的教训汇成一句

**适用性判据要贴着被测量的东西。** 代理越好用，越容易把不该判的拖进来，
而"多判"的后果不是更安全，是**门永远打不开**——
和"少判"一样糟，只是方向相反。

用户指定方向：把最终合成校验搬进搜索循环，校验不过时把冲突反馈给搜索，

|---|---|

## #58 「审美太差」是真的：器件挤成一团，纸用了不到三成

用户看完总览说"这是严重的 bug，审美太差了"。**判断正确。**

### 先排除了两件事

| 怀疑 | 实测 | 结论 |
|---|---|---|
| 几何在图纸外（坐标是负的）| `sch compose` 会重新装行并输出 `usableBounds`（"1 modules, 7 parts, 1 rows, maximum row height 345"）| 局部坐标系，合成时平移，**不是 bug** |

| 模块 | 间距 0 | 80 | 120 | 选定 |
|---|---|---|---|---|
| M1 | 52% 宽 | 68% | 失败 | **160（80%宽 / 50%高）** |
| M2 | 35% | 38% | 42% | **160（49% / 39%）** |
| M3 | 20% | 43% | 60%但仅 18% 高 | **80（43% / 36%）** |
| M4 | 21% | 32% | 45% | **160（54% / 44%）** |
| M5 | 45% | 54% | 太宽 | **80（54% / 27%）** |

## #61 坐标系打通了：文字判据第一次真正可判

上一轮卡在 `zone violates page padding`。本轮**读代码**解开，并把文字度量做成可用。

### 一、`zone violates page padding` 的真因

读 `schPreviewRect`（不是猜参数）：

```go
MinX = p.X
MinY = p.Y - (框高)      // 矩形往下展开
MaxX = p.X + (框宽)
MaxY = p.Y               // 上沿就是 p.Y
```

**`sheetPosition` 是 zone 的左上角，不是原点。** 我原来给 `{0,0}`，
整个框落到负 y，必然越界。

还有两条连带约束：

| 约束 | 来源 | 我原来错在哪 |
|---|---|---|
| 坐标要落在 5-raw 网格 | `plFloor(v)=floor(v/5)*5` 校验 `p.X==plFloor(p.X)` | 给了非整格坐标 |
| 框必须包住**渲染器认定的全部内容** | `powerLayoutContentObstacles` | 只按器件 bbox 外扩，漏了网标实体 |

把框扩到 `器件bbox±400`、图纸也扩到能容纳它之后，渲染成功。

### 二、画布 ↔ 页坐标的换算（精确解出）

用 SVG 里**图纸边框矩形**做锚点（它和 `sheet.bounds` 等大），实测公式：

```
canvas_x = (orig_x - bounds.minX) + ox
canvas_y = (bounds.maxY - orig_y) + oy
```

M3 实测 `(ox, oy) = (20, 85)`。**双向验证**：U3 本体 bbox `250..300 / 140..180`
→ SVG 里那条 rect 是 `x=1070 y=1705 w=50 h=40`，代入公式完全吻合；
`U3` 文字锚点换算回页坐标是 `(250, 184)`，正好在本体左下角。

### 三、两个必须避开的坑

1. **不带 `sheet` 渲染 = 两套坐标系。** 渲染器自己装行，文字落在它的
   viewBox 里，喂进验收立刻报 10 项越页 + 24 项相压 —— **全是错位假象**。
2. **实测 bbox 是设备像素，文字锚点是 viewBox 单位。** 差一个
   `k = viewBox宽/设备宽`。而且**按下标配对会串行**（实测把别人的框配给了
   `svgtext-6`），必须按"内容 + 最近位置"配对。

第 2 条我一开始两个都犯了，报出 24 项越页；改成按内容配对后 **0 项越页**。

### 四、对齐后的真实结论（M3）

| 判据 | 结论 | 说明 |
|---|---|---|
| 内容不越框 | ✅ **PASS** | 配错框时是 FAIL，现在是真 PASS |
| 模块框不切器件 | ✅ PASS | |
| 导线不穿器件本体 | ❌ FAIL 3 | 导线穿**引脚名文字框** |
| 遮字/文字相压 | ❌ FAIL 17 | 见下 |
| 其余 | ⛔ NOT RUN | 缺宿主证据 |

**这 17 项查清了：全部是引脚名（EN/FB/GND/IN/LX）画在 U3 自己本体内。**
箱形符号把引脚名写在框里是正常画法，属**缺归属信息的误报**——
文字图元没有 `ownerPartId`，检查器只能当自由文字处理。

### 五、结论

- 坐标系打通了，**文字判据第一次可判**（不是靠编数据）
- 剩下的 17 项是**归属缺失**导致的误报，修法是给文字图元补归属，
  不是去挪引脚名
- 钉了 5 条换算测试：锚点按尺寸定位、本体框往返一致、无 sheet 必须报错、
  页眉要被过滤

**只有坐标系对齐之后，"文字类通过/失败"才第一次有意义。**

## #63 「导线穿位号」的修法找到了，但只做通了一半

上轮剩下唯一真缺陷：**导线穿过位号文字**（五块全有）。本轮去找它的修法。

### 关键发现：路由器**本来就避让文字框**

读 `validateLibRoutingEdge`：

```go
for _, box := range component.TextBBoxes {
    if plSegmentTouchesBox(a, b, box) {
        return schWireObstruction(p, "wire-text", ...)
    }
}
```

也就是说求解器**愿意**避开文字，只是我的排版输入**从来没给 `textBboxes`**。
这就是那条缺陷一直存在的直接原因。

### 实现（`sch_layout_input.py --designator-reserve`）

位号落点按渲染器规则（读 `sch_layout_render.go:240`）：
`text(bbox.MinX, bbox.MaxY-4, 7, ...)` —— 本体左上角上方、字号 7。
据此给出预留框，宽度按 `0.62 × 字号 × 字数`。

### 实测：一半成、一半败

| 模块 | 加预留区后 | 加之前 |
|---|---|---|
| M3 | ✅ 可解 **1.2 秒** | ✅ |
| M4 | ✅ 可解 **1.3 秒** | ✅ |
| M5 | ✅ 可解 **0.3 秒** | ✅ |
| **M1** | ❌ **40 万候选内解不出** | ✅ 8 秒 |
| **M2** | ❌ **40 万候选内解不出** | ✅ |

而且即便解出来，渲染阶段又报：

```
zone M3 geometry: component label reservation collision: C13/U3
```

→ **位号与位号之间的预留区没有互相避让。**

### 结论：默认关闭

`--designator-reserve` 是**默认关闭的开关**。理由很实在：
开着会让原本能解出来的 M1/M2 解不出来 —— 那是把工具弄坏，不是改进。

做完"排版把位号预留区算进器件占位"（布局层改动）之前，这个能力不能默认开。

### 顺带修的两个真 bug

1. `sch_layout_input.py` 里 `problems_by_page` **先用后声明** →
   多页输入直接 `UnboundLocalError`（本该是一句"请用 --page 收窄"）。
   由新测试撞出来。
2. 该变量被声明两次，第二次会把前面的追加**清空**。

离线链 S6 报 `c6.ie2 必须有且只有一个：网/NC/unconnected`。
根因是**引脚几何缓存重新测量**后多出一个 `ie2` 引脚（日志 "命中缓存 38，新取 1"），

## #68 文字互压清零：M1 6→0、M2 5→0，五块验收升到 5 PASS

### 缺陷到底是什么（查了内容才敢改）

```
text_overlap  'A'@(199,206) × 'K'@(195,206)     ← 同一颗二极管的两个引脚标签，相距 4 raw
text_tight    'C11'@(303,251) × '2'@(312,246)   ← 位号压住引脚标签
text_overlap  '1'@(190,106) × '2'@(194,106)     ← 相邻引脚号
```

`sch_layout_render.go` 原来对**每个引脚无条件画一次标签**，字号 4.5、

- 与已占框**相接也算冲突**（原来用 `<`，相距 4 raw 的 `A`/`K` 判不出来）
- 冲突就跳过这个标签；**框照画、引脚圆点照画**，完整信息仍在 `<circle><title>` 里

| 没算位号/值占位 | `C11` 仍压 `2` | 位号框、值框先入清单 |

第一版改完 M2 还是 5 项 —— **如果不重新量，就会以为修好了**。

## #69 「导线穿位号」试了四条路，全部走不通 —— 这次**回退，不留半成品**

剩下唯一 FAIL 是导线穿位号（五块）。本轮把能想到的路都试了，**每条都用数据判定**。

### 路 1：把位号预留区交给求解器（`textBBoxes`）

| 模块 | 结果 |
|---|---|
| M3 / M4 / M5 | ✅ 可解（1.2 / 1.4 / 0.3 秒）|
| **M1 / M2** | ❌ **100 万候选（上限）仍解不出**（116 秒 / 19 秒）|

### 路 2：给摆放加"位号预留区互撞"判据

新增 `libValidateLabelReservations`（**只在有 TextBBoxes 时生效**，默认行为不变），
两条规则：预留区互撞、预留区压别人本体。

结果：**M1/M2 依旧解不出**（40 万候选内失败），说明卡的不是这条。

### 路 3：按实测校正预留框

实测渲染器把位号画在 `x∈[minX-2, minX+tw]`、`y∈[maxY, maxY+8]`，
而我原来的框是 `y∈[maxY+2, maxY+13]` —— **下沿差 2 raw，导线正好从那条缝过去**。
按实测校正后重排 M3……**缺陷仍是 3 项**。

### 路 4：把位号挪到本体下方

既然线是从**左上角附近的引脚**引出的，位号挡在出口上，那就把位号挪到下方。

结果：**`frame_border_crosses_object` 立刻 FAIL** —— 位号掉出模块框。
**这是打地鼠**：躲开导线又切了框。

### 判定与处理

四条都不通，**回退路 3/路 4 的实验**，回到上轮状态（五块 5 PASS / 1 FAIL），
只保留两样真有用的：

| 保留 | 理由 |
|---|---|
| 位号预留区校验（opt-in） | 只在给了 TextBBoxes 时生效，默认不变；能让冲突在**摆放期**而不是渲染期暴露 |
| 上轮的引脚标签去重 | 文字互压 6/5 → 0，是实测有效的 |

### 为什么这条路走不通（结论）

位号被画在**本体左上角外侧**，而该器件左上角附近**有引脚**时，引线只能朝外走、
必然穿过位号带。要么改位号落点（会掉出框），要么整体重排（会解不出来）。

> **这是"标签落点"与"引脚出口"的布局级冲突，不是渲染偏移能解决的。**
> 真正的解法需要让**标签位置成为布局的一等约束**（像器件本体那样参与占位与评分），
> 那是排版引擎的结构性改动，不是本轮能安全完成的。

### 记录

- 新增 3 条 Go 测试钉住预留区校验：无 TextBBoxes 不生效、互撞要拒、压别人本体要拒
- 五块验收维持 **5 PASS / 1 FAIL / 3 NOT RUN**，缺陷如实保留
